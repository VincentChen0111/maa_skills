由此得出的结论（核实后采用）：

- **时间段重叠时 MAA 选哪一个**：选文件里靠前的那个计划。所以检查把两个计划的时间段重叠（`a 开始 < b 结束` 且 `b 开始 < a 结束`）记为错误 `period-overlap`；首尾相接（一个在 08:00 结束、另一个在 08:00 开始）不算重叠，是覆盖全天的写法。
- `hh:mm` 写不出 24:00，`23:59` 结束的计划在 23:59 到 24:00 这一分钟不被选中，MAA 用第 0 个计划。这是协议本身的写法，检查把 `23:59` 当作一天结束，只在验收门 14 的证据里说明这一分钟。
- **计划数上限**：MAA 没有上限，只要求 `plan_index` 在范围内。所以「计划数上限」这条规则实现为：至少一个计划，并且等于用户的班次数（`plan-count`），不另编一个经验上限。
- **生产线**：规格「共享工具」写的是「MAA 不能切换生产线」。固定版本的源码里，自定义模式写了产物、而游戏里的产物不一致时，MAA 会尝试切换（双芯片除外）。所以这条规则实现为「方案不依赖 MAA 切换生产线」：导出时不写产物字段；检查已有排班文件时，产物必须是 MAA 认识的值、属于该设施，并且和用户布局里的当前产物一致，否则是错误（`product-invalid`、`product-switch`）。规格正文已经改成这个说法，需要维护者知道这一差异。
- **键名大小写**：设施键和字段名都按字符串精确比较，写错大小写的键被当作不认识的键跳过，所以大小写写错是错误（`key-case`）；导出时基础文件里大小写写错的已知键会去掉并在结果里列出。
- **菲亚梅塔的 `post`**：两步在所有设施换班之后执行，第一间宿舍最后只剩目标和菲亚梅塔：宿舍 1 名单里的其他人被清出，整班不恢复心情；目标也离开它工作的房间，直到下一次运行。所以生成拒绝 `post`（`shift-fiammetta-post`），检查已有排班文件时第 11 项不通过，只用 `pre`。时间线仍按 MAA 的做法算 `post`，第 4、5、14 项的结论也是真实的。
- **跳过的房间**：`skip`（以及数组比房间少时没配置的房间）保持原样，里面的人继续上班。所以某一班没安排的房间，上一班放进去的人留在原处，时间线按这一点算（第 5 项会把他们算作每个班次都在岗）。
- **运行时间和选计划**：图形界面在每次运行时按当时时间（带秒）比较 `hh:mm`，两端都含。运行总在那一分钟的几秒之后，所以时间段最后一分钟里的运行已经不在这一段里，23:59 那一分钟里的运行退回第 0 个计划。提前运行如果落在这一班时间段的开始之前，选到的是还在进行的上一班计划，这次运行把上一班的人重新放一遍；之后的运行如果仍在上一班的时间段里，上一班一直上到下一次选到别的计划的运行。

## 规则和验收门的判定（实现时定）

六条规则：房间容量（`room-capacity`，布局外的房间 `room-missing`）、计划数（`plan-count`）、同一计划内不重复（`plan-duplicate`，宿舍也算）、键名大小写（`key-case`）、不依赖 MAA 切换生产线（`product-invalid`、`product-switch`）、未持有警告（`operator-unowned`）。另外：名字不在用户本机 MAA 名表里是错误 `name-unknown`，和未持有警告分开；名表读不到时记为未核实 `names:<原因>`；排班文件按显示名写人，固定表里有 9 个显示名对应两个游戏 ID（8 个是预备干员，只有「暮落」带基建技能），这时取快照里持有的那个形态；快照里一个都没有就是未持有警告，两个都有就记未核实 `ownership-ambiguous:<名字>`，技能按未知处理；时间段格式错误 `period-format`、重叠 `period-overlap`、只有部分计划带时间段 `period-mixed`。

15 项验收门，每一项都给出通过、不通过或未核实，并附证据；任何一项不通过或有错误，方案就不可应用；未核实的项单独列出，不算通过：

第 3、4、5、11、12、14 项共用一条时间线（`checkPlanText` 里的一个实现）。时间线照 MAA 的实际做法逐次运行：每到用户的一次 MAA 运行时间（输入 `runs`；不给时取时间段里换计划的时刻），按上面的规则选计划（运行落在那一分钟的几秒之后）；没有时间段时按文件顺序每次换下一个计划。选好后，每个写了名单的房间清空再放入名单里的人，跳过的房间保持原样；菲亚梅塔的两步按 `pre`/`post` 放在设施换班之前或之后，她满心情时和目标互换心情。两次运行之间，工作房间里的人按每小时消耗减少心情（低于 0 的那一刻记为降到 0），宿舍里的人按每小时恢复增加、不超过上限（菲亚梅塔按她技能的每小时 2），不在任何房间的人心情不变。从满心情开始按周期模拟（一天；没有时间段而给了运行时间时，按轮换和天数重新对齐的天数），直到某个周期的开始状态和 1 到 4 个周期之前相同，读这一循环里的结果；64 个周期内不重复时，每周期心情还在下降的人算不通过，其他情况未核实。没有时间段也没给运行时间时只知道顺序，心情相关的项未核实。`tests/base-plan-conformance.test.ts` 用一份独立写的逐分钟 MAA 模型（同样按上面引用的源码行写成，不调用检查代码）核对第 4、5、11、14 项的结论：117 份方案，覆盖两班和三班、一个计划几段时间段、菲亚梅塔不用和 `pre`/`post`、按时和提前、推迟运行，每份四项结论都要和模型一致。

1. 同一计划内名字不重复（宿舍也算）；一个周期内同一 `spCharGroups` 分组只用一个形态。名字对不上唯一游戏 ID 或异格表不可用时未核实。
2. 容量和房间存在用固定表和用户布局判定；快照里没观察到的名字是警告，这一项记未核实（识别完成不代表名册完整，未观察不等于没有）。
3. 计划数等于用户的班次数；每个布局里有的设施都写了键，间数和布局一致；布局里没有的设施不写人；给了 `runs` 时每个计划至少被一次运行选中。
4. 在时间线的稳定循环里没有人心情降到 0；证据写出那一段从几点起连续上班、几小时、每小时多少、开始时的心情和几点降到 0。每周期心情净减少的人也不通过。速率是输入（报告里标为推断），没有速率、没有心情上限或时长未知时未核实。
5. 没有干员在稳定循环里每次运行之后都在工作房间（跳过的房间里留下的人也算在岗）。例外是菲亚梅塔的目标，要同时满足：每次运行都有和它的互换；每次互换都发生（见第 11 项）；它每小时消耗不超过菲亚梅塔每小时的恢复（取自技能原文，固定表是 2）。少一条就不通过，算不出时未核实。
6. 床位总数 = 布局里宿舍的床位之和（固定表）；常驻 = 每个计划都在宿舍且从不上班的人；每个计划里在宿舍的其他人 ≤ 床位总数 − 常驻人数。由 MAA 自动补满的宿舍在证据里注明。
7. 声明的组合：任一成员在上班的计划里，所有成员都在上班，依赖的挂件干员在岗或在宿舍。没有声明组合时未核实（本工具不从技能文字推断组合）；声明为空列表表示「没有组合」，记为通过并标明是推断。
8. 声明的互斥：同一计划里，贸易站和制造站里不能同时出现两名以上互斥成员。声明方式同第 7 项。
9. 制造站、贸易站里每名干员：有作用于该房间产物或不限产物的生效技能就通过；生效技能全部写明只作用于别的产物（固定表原文「作战记录类配方」「贵金属类配方」「源石类配方」「芯片类配方」，贸易站「赤金订单」「贵金属订单」「合成玉订单」）就不通过；技能状态待核时未核实；没有该房间技能的算填充，写进证据。
10. 控制中枢人数等于按等级的容量；同一个技能 ID 不在两名干员身上同时生效。
11. 每个计划最多一个无人机目标，目标在布局里（间号 1 到 min(5, 该设施间数)）；菲亚梅塔有目标、顺序是 `pre`（`post` 不通过，理由见上面的 MAA 事实和结论）、目标在这个计划里，并且快照里有菲亚梅塔（按她的宿舍技能找 ID）。协议每个计划只有一个菲亚梅塔对象，由 MAA 在换班这一次运行里使用，所以「只在班次开始时、每个节点最多一次」由结构保证。稳定循环里配置的每次互换都要发生：时间线里她在那次运行时不是满心情就不通过，证据写出她当时的心情；她不在任何计划的宿舍名单里时会在互换后被换出宿舍、恢复不了，证据里写明。算不出时未核实。
12. 每条效率数字的总效率 = 基础 + 技能 + 全局；给了总数而对不上就不通过；每日数值 = 各计划总效率按这个计划在时间线上的上班时长（从选中它的运行到下一次运行）加权平均；没有时间线时按时间段长度。没有效率数字时未核实。
13. 生成时导出两次并读回写入的文件，三者逐字节相同；报告的新鲜度检查用报告里记录的导出内容和当前文件比较；不是本工具本次导出的文件未核实。
14. 时间段覆盖全天（MAA 在没被覆盖的时间退回第 0 个计划，所以有空档就不通过）。早晚运行：从稳定循环开始，下一个周期里只挪动一次运行，挪动量取容差的两端（提前和推迟整整容差时长），再加上容差以内 MAA 改选计划的地方的两侧（例如时间段在运行前 45 分钟开始、容差 1 小时时，也试提前 45 分钟和 46 分钟）；挪动后的运行按它实际的时间选计划，之后照常运行四个周期。每一种挪动下都没有人心情降到 0 才通过；按时运行已经有人降到 0 时这一项也不通过。同一次运行挪动得更少、选到同一个计划、结果相同的证据只写一次。提前运行落在这一班时间段之前时，MAA 选的是还在进行的上一班计划，这次运行把上一班的人重新放一遍，上一班一直上到下一次选到别的计划的运行（两班都在时间段开始时运行的方案，07:00 提前运行后 20:00 那次仍选夜班，夜班连续上 36 小时）；证据写明这一点并给出改法：把这一班时间段的开始提前到「运行时间 − 容差」或更早（前一段相应提前结束），MAA 仍在原来的时间运行，并把运行时间写进 `runs`。不写 `runs` 时检查把时间段里换计划的时刻当成运行时间，只挪时间段等于把运行时间也一起挪了，所以改法必须同时写 `runs`。容差设为 0 时不检查。没有时间段时 MAA 按顺序轮换，挪动不改变选中的计划。
15. 标题、计划名、描述、理由、依据、假设和总体推断里没有「最优」「最佳」「最好」「最强」「最高效」或 optimal/best 一类说法；用户自己的原话不算。

## 数据新鲜度（实现时定）

三态：新鲜、陈旧、未知。每一项都和报告生成时记下的内容比：

- 账号快照：比较干员 ID、名字、精英阶段、等级、干员识别状态和基建布局字段算出的指纹；读取时间和扫描时间不参与，晚些重读到的相同内容仍是新鲜。现在读不到或格式不对是未知。
- 基建技能表：比较每个固定文件的仓库、提交、路径和内容 SHA-256；现在读不到（例如断网）是未知。
- MAA 干员名表：比较 `resource/battle_data.json` 的内容 SHA-256；没设 MAA 目录或文件不在是未知。
- 排班文件：比较文件内容的 SHA-256；文件不在是未知。
- 检查结果：上面任何一项陈旧就是陈旧，否则有未知就是未知，全部新鲜才是新鲜。不新鲜时旧的检查结果不当作证明：`freshness` 用当前数据把检查重新跑一遍并返回新结果（不改报告），第 13 项拿报告里记录的导出内容和当前文件比较。

## 写排班文件

只写私有目录里的路径：路径解析后（包括经过链接）落在私有目录之外就拒绝（`plan-path-outside-private`），拒绝前不在私有目录外创建任何目录，只接受 `.json`（`plan-path-invalid`）；先写同目录的临时文件再改名替换；默认文件名带内容哈希（`base-plans/plan-<前 16 位>.json`）。在已有排班文件上修改时（`base`，也必须在私有目录里），MAA 协议里的字段由本工具重写，其他字段（包括扩充协议的 `layout`、`operators`、`metadata`）原样保留，大小写写错的已知键去掉并列出。检查也只读私有目录里的排班文件。

## 设计默认值（2026-11-13，不是维护者原话）

- 早晚上线的容差默认 1 小时（理由：`hh:mm` 粒度下能发现正好卡在心情上限上的方案，用户可以调大）。
- 心情时间线、菲亚梅塔互换能否发生、早晚运行的算法见上面「共用一条时间线」一段和第 4、5、11、14 项（独立审查第 1、2 轮的意见按 MAA 源码和固定游戏表修正）。
