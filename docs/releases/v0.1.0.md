## MAA 版本

下面两行由 `node scripts/maa-version-check.ts notes` 按随包核实记录（`skills/maa-core/references/verified-versions.json`）生成，发布时检查脚本逐字核对：

MAA 源码已核：v6.22.0

MAA 实机已核：无（没有在真实 MAA、模拟器和游戏上核对过的版本）

- **源码已核**：v6.22.0。意思是本仓库依赖的每一条 MAA 行为，都在 v6.22.0 的源码上对过指纹（[依赖条目](../maa-dependencies.json)，做法见 [MAA 版本跟踪的来源](../maa-version-sources.md)）。源码相同不等于在真实环境里跑通过。
- **实机已核**：无。本仓库还没有在真实 MAA、模拟器和游戏上核对过任何版本。离线测试、合成 GUI 用例、宿主替身和机器评分都不算实机核对；起点 skill 在 MAA v6.21.4 上的实测经验是另一个项目的历史，也不算本仓库的实机核对。
- `maa-setup` 和 `maa-doctor` 按这份记录提醒：装的 MAA 版本不在列表里时只提醒，不拒绝运行；装的版本低于某个源码已核的正式版时提醒升级，并说明那个版本是否实机已核。升级由用户自己完成。

## 包含什么

五个 skill 和一个共享目录，正文都是中文，两个宿主共用：

- `maa-help`：只用文字回答能做什么、用哪个 skill、怎么安装和更新。
- `maa-setup`：接入或补齐 Windows 图形界面版 MAA、国服模拟器、adb 和 Node 24；下载前先展示官方下载方案，用户确认后才下载；凭据由用户在自己的终端输入。
- `maa-account`：账号快照（MAA 本地识别结果，或森空岛只读）、培养成本与缺口、基建技能查询、带出处的只读调研、带独立审查的培养建议与基建建议。
- `maa-daily`：按当次交办或已批准的报告维护日常队列、提醒、定时，准备指定关卡作业并跟踪结果，专精排程，应用已批准的基建排班。
- `maa-doctor`：分组检查、日志分析与转介、遗留写入核对与恢复，修法逐项点名批准。
- `maa-core`：操作类 skill 共用的脚本，不直接处理请求，要和操作类 skill 装同一版本。

只支持 Windows 上的 MAA 图形界面版和国服；共享脚本需要 Node 24。不打包 MAA 的代码和资源、游戏数据、企鹅物流和一图流的数据，用的时候再读取。

## 试用修复（2026-11-16）

维护者 2026-11-16 在 Codex 里手动试用了重建之前的候选，试用发现的问题由三个修复合入这个候选（#105、#106、#107）。对用户的变化：

**专精无人值守续接（maa-daily，#106）**

- 专精按已批准的培养计划无人值守续接：一档完成后接着准备下一档；一个干员的计划完成后，按已批准的培养报告条目准备下一位干员。训练室同一时刻只由一个计划占用，前一个计划完成后才准备下一位。无人值守时遇到只有用户能确认的事（例如上一个计划停在已知矛盾，或者没人能确认 MAA 已关闭）就停下并说明原因，不自己关闭计划，也不替用户确认。
- 只有「单次协助满五小时，下次训练时间减半」这类条件的助手照常可用：核实不了的加速条件按已核实的部分估算，标为下限并列为待核，多档计划不再在准备时失格。
- 正在训练、材料已经扣过的档次不再重复计材料：可以由用户确认，也可以从森空岛快照的训练室受训者信息看出来；读库存之后才付料的档次从库存里预留。
- 训练室等级和配方房间等级取自账号快照；准备计划要的事实和开训要的事实分开，开训要的事实存进计划，下次进入时刷新后再开训。

**材料缺口：加工到基础材料，材料券建议（maa-daily 专精、maa-account 缺口，#106）**

- 缺材料时除了缺的成品，还说明加工之后还要获取的基础材料和数量，以及龙门币缺口（含加工费）。
- 材料券：先问用户各券的数量和是否有效；用户不回答，也给不依赖数量的建议（例如「有这种券的话，优先换 X」），不编造数量，也不把券算进已核覆盖。
- 缺口（包括龙门币）不会让计划被判为不可行，也不阻止计算、展开、准备或推进计划；只有某一档真正开训时要这一档的材料到齐，每次进入时重新核对。
- 用户亲口批准加工时，开训门接受 MAA 培养任务能在加工站补齐的缺口：MAA 开专精缺料时会在加工站自动合成缺的部分（没有开关），消耗下级材料、龙门币和加工站干员的心情，可能换掉加工站里的干员且不换回。材料券路线不算进开训门（MAA 不兑换）。
- 配方要求的关卡没确认时，用户可以把工具报出的关卡一次确认，不必逐个回答。

**关卡作业按真实数据核对（maa-daily，#105）**

- 作业要求的专精、技能等级和模组按 MAA 作业协议核对快照里的真实数据。MAA 识别快照没有专精、模组数据而森空岛快照有时，改读整份森空岛快照（两份不合并），回复说明读的是哪份、为什么、读取时间；培养成本、培养报告和基建技能查询也用同一条规则。已知不够的记为不满足，满足的可以准备，只有真的未知才待核。
- 用户核实过的干员事实（例如某个干员的专精和模组等级）可以告诉 agent 后再查询；也可以对一份作业整份确认一次，只覆盖只有用户能核对的待核项，只用于这一次。
- 一份作业的内容 MAA 用不了（例如干员组与单个干员同名）时只挡这一份，同一关的其他候选照常给出。
- 前置关卡没核实时写出具体是哪一关，所有没核实的前置合成一个问题，只问一次。
- 请求没写 MAA 版本时读已安装 MAA 的版本，并在报告里记下来源。

**「需要核对」说具体（共享脚本，#105、#106）**

- 脚本要用户核对时，统一给出具体的原因码、要核对什么和有没有替代办法（`reason`、`check`、`alternatives`），agent 照这三项转述，不只说「需要核对」；训练接口另给出还缺哪几项事实。其余命令行入口的兜底失败也走同一个出口，带固定代码的拒绝和退出码不变。
- 试用之后对「过度阻挡」做了复核（OB-1 至 OB-9），跟进都在上面几条里：坏作业只挡自己，前置只问一次，自动读 MAA 版本，有数据就用（快照选择、训练室等级、受训者信息、关卡一次确认），核实不了的加速条件按下限估算。

**写入配置只带会变的字段（maa-daily，#107）**

- maa-daily 写入 MAA 配置时，请求只带值会变的字段：用户提到的某一项已经是要的值时（例如活动临期药本来就是关的），不写进请求，并告诉用户这一项本来就是这个值、没有改。

**这些修复的验证**

- 离线测试（每项先写失败测试）和各自的独立审查都已做完；每个修复 PR 合并前在自己的冻结框架上跑过 Codex 前后评测，记录在仓库的验证文档里。是否发布以这个重建候选上的评测为准，见下面「验证状态」。
- 只核对了源码、没有实机核实：MAA 作业协议里专精、技能等级和模组的写法（v6.21.4、v6.22.0 源码）；MAA 开专精缺料时在加工站自动合成（v6.21.4、v6.22.0 源码；合成数量上限和心情不足时的表现没有核实）。
- 要用真实响应核对：森空岛训练室受训者的字段（正在练的技能、剩余时间）还没有用真实的森空岛响应核对过。
- 没有评测场景：维护者试用要求的两项，训练流程里的材料券建议（缺口查询里的材料券建议有场景核对，训练流程里没有），和养成报告里加工展开到基础材料的那一段（养成报告已有的场景都不核这一段）。
- 没有测过：森空岛数据比游戏内滞后多久（回复里照实写明）；作业选「不用模组」时 MAA 怎样处理没有分支页的干员，只是读代码得出的推论；自动读 MAA 版本没有评测场景，只有单元测试。

## 安装与更新

- Claude Code：`claude plugin marketplace add VincentChen0111/maa_skills`，再 `claude plugin install maa-skills@maa-skills --scope user`。插件以仓库根目录为插件，全部 skill 和 `maa-core` 一起装好。
- Codex：用自带的 skill-installer 按 `skills/<名称>` 安装，`maa-core` 要和操作类 skill 一起列出，固定到这个版本的标签。安装器不覆盖已有目录，更新时先在临时目录装好验证，再整体重装全部 `maa-*` 目录。
- 详细步骤见 [宿主与安装](../../skills/maa-help/references/hosts.md)。
