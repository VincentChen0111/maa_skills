# 05 未来进程状态记录的诊断与修复

基点：`8d277ede5947c6a12dd7aec92e87fa371f0c4f47`。本记录只覆盖进程日志判断的已复现机制，不代表工单 05 产品 R5、模型或真实 MAA 通过。

## 原始失败与证据边界

[Windows CI job 130100985295](https://github.com/VincentChen0111/maa_skills/actions/runs/42893660808/job/130100985295) 的 196 项测试为 194 通过、1 失败、1 跳过。失败在 `tests/maa-process.test.ts` 的「a new busy state is checked again before sending a normal close request」：预期 `maa-not-idle`，实际没有拒绝，耗时 319.2184 ms。失败后没有重跑该 CI 来掩盖结果。

CI 使用 GitHub 的临时合并提交 `8fcbaf1` 与 Node 24.22.2；本机使用 Node 24.22.1。通过 GitHub 文件接口核对，合并提交中的进程实现、对应测试和 Node 假进程夹具均与基点相同。原 CI 未保留失败当时的合成日志及父子进程时间记录，不能据此认定本记录的机制是该次失败的唯一根因。

所有探针在隔离工作树、真实临时目录运行，仅替代 MAA 进程边界。没有替代 Date、文件系统或系统进程观察，也没有操作真实 MAA、设备或用户安装。原 CI 日志、每次真实进程 PID/启动时间、IPC 确认、关闭请求时间和完整合成 GUI 日志保留在本机忽略目录。

## 公开接缝复现

原单测单独运行通过；以同一 `createMaaProcess` 接缝、原假进程及真实文件执行 200 次带事件记录的探针，也未观察到缺失拒绝。不过其中 7 次，子进程已写入的忙碌记录时间比父进程接到写入确认时的 `Date.now()` 领先 1 ms；二次进程列表观察时均已追平。

随后只改变允许替代的合成 MAA 边界所提供的日志时间，保持文件落盘确认、真实时钟、PID、启动时间和产品实现不变：

| 合成忙碌记录相对子进程实际时间 | 缺失拒绝 / 调用数 |
| --- | --- |
| 0 ms | 0 / 30 |
| +1 ms | 0 / 40 |
| +2 ms | 5 / 30 |
| +20 ms | 5 / 5 |

失败记录确认：忙碌行已落盘且已收到 IPC 确认；选中的进程身份及当前会话正确；正常关闭请求在该行时间之前发出。`sessionState` 原先直接跳过未来行，却保留更早的 `ready=true`、`idle=true`，因此公开 `close()` 正常完成。确定性复现命令为隔离工作树中的 `node .tmp/repro-busy.mjs 5 20`；修改前产生 5 次「Missing expected rejection: maa-not-idle」。这证明了过滤未来状态后仍保留安全结论的机制，没有证明 CI 当时实际发生了多大的时钟差。

## 最小修复和验证

先在公开 `createMaaProcess` 接缝增加回归：以真实临时文件写入足够未来的当前会话忙碌记录，旧实现仍正常关闭，测试以缺失 `maa-not-idle` 拒绝失败。随后修复当前会话的 RunningState、Bootstrapper、AsstProxy 未来记录：其时间未获确认时，本次读取返回未就绪、非空闲，正常关闭继续按既有 `maa-not-idle` 拒绝。当前会话之前的记录不替代当前状态；后续已观察到的新会话重新建立状态。

回归同时覆盖未来 idle/init、未来启动或资源错误不能保留旧安全结论，以及新会话不被旧会话的时间异常污染。原有当前状态变化、旧会话过滤、进程身份、退出树与临时 Windows GUI 事务测试保留。没有添加等待、重试或时钟容差；没有更改 skill、评测框架或模型场景。

这是[既有未知进程状态不猜安全约定](../daily-verification.md)的修复，不增加新的操作授权或时间预算；为使实现边界可追溯，仍在[规格的两张来源表](../spec.md)登记未来状态的具体处理。诊断与实现验证不是产品独立审查，不替代尚未获准的 05 产品 R5。
