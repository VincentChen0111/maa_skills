## 问题陈述

用 MAA 的玩家希望 Codex 或 Claude Code 帮忙做这些事：
- 装好并配置 MAA；
- 弄清自己账号的家底，拿到培养和基建建议；
- 日常改配置、刷指定关卡、排专精。

2026-11 查过，还没有面向普通玩家、能做这些事的公开 skill（见「其他说明」）。

维护者自己现在的做法，散落在一个越来越大的 skill 和一份私人手册里：
- 功能越加越多。一份手册里装着授权、环境、待办、材料、经验好几类内容。
- 两个 agent 同时改 MAA 配置时，是否冲突只能看日志去推断。
- 培养和基建分析没有固定流程。
- 同一个工具在不同地方各有一份实现。

## 方案

建一个公开的 MIT 仓库，提供五个 skill，Codex 和 Claude Code 都能装：

- `maa-setup`：从零装好 MAA 和周边环境，已经做过的步骤自动跳过。
- `maa-account`：扫描账号，生成账号快照，给出培养和基建建议报告。
- `maa-daily`：日常改 MAA 配置、刷指定关卡、排专精、设单次定时。
- `maa-doctor`：诊断问题，经用户同意后修复；MAA 自身的问题转介出去。
- `maa-help`：只用文字告诉用户有哪些功能、该用哪个 skill、怎么安装，自己不做任何操作。

另有一个共享脚本目录 `maa-core`，供四个操作类 skill 调用，不是面向用户的入口。

几条总原则：
- 每个 skill 按「能写什么」划定边界。
- 用户数据全部放在仓库外的私有目录。
- 安全边界写死。
- MAA 发新版本时，由自动核对来跟踪。

## 实现决定

### 仓库与打包

- 公开仓库，采用 MIT 许可证。
- 不打包 MAA 的代码和资源，也不打包游戏数据、一图流数据和企鹅物流数据，用的时候再取：
  - MAA 的数据从用户本机读取；
  - 中文游戏数据表从公开的游戏数据镜像按固定提交读取，实现时写明是哪个仓库，并注明出处；
  - 材料价值来自一图流；
  - 掉率来自企鹅物流。
- 每个 skill 一个目录，入口是 SKILL.md，旁边放参考文件和脚本。
- 同一套目录结构，既能用 Claude Code 插件市场安装，也能用 Codex 的 skill-installer 安装。仓库根目录放 Claude 插件和插件市场的描述文件。
- 两种安装方式都是原样复制目录，所以 SKILL.md 要写成两个宿主通用。宿主之间的差异（比如独立审查怎么发起）写在一份宿主说明参考文件里。不另写复制安装脚本。
- 共享脚本集中在 `skills/maa-core/`。它不是操作入口，但带一份 `SKILL.md`，因为 Codex 的安装器要求每个被安装的目录都有。操作类 skill（setup、account、daily、doctor）通过相邻目录 `../maa-core/scripts/` 调用，每个脚本只有这一份实现。
- 操作类 skill 开始前先确认相邻的 `maa-core` 存在。缺失时不继续操作，按宿主告诉用户怎么补装；这段指引写在每个操作类 skill 自己的 SKILL.md 里，因为此时 `maa-core` 里的文件读不到。
- 维护者开发时，用目录联接把两个宿主的 skill 目录指向本地 clone。
- skill 正文用中文。README 以中文为主，开头附英文简介。
- 只支持 Windows 上的 MAA 图形界面版，服务器只支持国服。
- 共享工具需要 Node 24，直接运行 TypeScript 源码。

### 五个 skill 和边界

| skill | 读 | 写 | 不写 |
| --- | --- | --- | --- |
| `maa-setup` | 环境、MAA、模拟器 | 设置文件（经偏好脚本）、私有目录骨架、环境记录、MAA 配置里的连接类设置（经写入脚本） | 账号快照、报告 |
| `maa-account` | 游戏（经 MAA 识别）、森空岛、社区资料、私有目录 | 账号快照、建议报告 | MAA 配置 |
| `maa-daily` | 私有目录、建议报告、MAA 配置和日志 | MAA 配置（经写入脚本）、待执行和运行记录 | 账号快照、报告 |
| `maa-doctor` | 以上全部 | 最近一次检查的记录；用户同意某项修法后，经对应的写入通道修复 | 不另开自己的写入通道 |
| `maa-help` | skill 说明 | 无。只用文字回答，不运行脚本 | 一切 |

- 专精：「专哪个技能」属于建议，归 `maa-account`；「什么时候开训、选谁当助手、设定时」属于操作，归 `maa-daily`。
- 基建：「怎么排」属于建议；「写进 MAA 的自定义基建排班」属于操作。
- `maa-help` 只提供文字帮助：有哪些功能、某个需求该用哪个 skill、怎么安装。用户在 help 里要求改偏好时，help 说明由哪个操作类 skill 记录，自己不写。
- 四个操作类 skill 都可以做两件事：
  - 经偏好脚本改结构化设置，例如用户说「以后用英文」；
  - 把用户新的偏好原话追加进偏好原话文件，但不能改写旧条目。
- 调研工具（NGA、森空岛社区、B 站、作业站）属于共享工具层，不单独做成 skill。

### 私有目录与设置文件

- 设置文件固定放在 `%USERPROFILE%\.maa-skills\config.json`，记录语言、私有目录、MAA 目录和服务器。环境变量 `MAA_SKILLS_HOME` 可以改变它的位置，评测时就靠它指向临时目录。
- 设置文件只由偏好脚本写入：先写临时文件，再改名替换。
- 私有目录里按写入者分文件：
  - 偏好原话：四个操作类 skill 都可以追加；
  - 环境记录：`maa-setup`；
  - 账号快照和建议报告：`maa-account`；
  - 待执行和运行记录：`maa-daily`；
  - 最近一次检查的记录：`maa-doctor`。
- 通用经验（某个 MAA 版本的行为、游戏机制）写进 skill 的参考文件，随仓库走。只对某个用户成立的约定，放进这个用户的私有目录。
- 每个操作类 skill 开始时先读设置文件，按其中的语言回复和写报告。没设语言时，按用户第一句话的语言回复，并提示可以设置。`maa-help` 不读设置文件，按用户这句话的语言回复。

### MAA 配置写入

- 对 MAA 配置的所有改动都经过同一个写入脚本，在一个进程里依次完成：
  1. 确认现在可以写；
  2. 获取写入锁；
  3. 关闭 MAA；
  4. 备份；
  5. 只改必要的键；
  6. 重开 MAA；
  7. 读回核对；
  8. 记录改了哪些键；
  9. 释放锁。
- 写入锁以独占方式创建。锁里记录 skill、宿主、脚本进程号、开始时间和当前步骤。
- 遇到遗留锁时不直接删除：先对比最新备份和当前配置，确认 MAA 是否在运行，把结果报告给用户，核对完才清除。
- 写入锁管不到的情况，处理方式如下：
  - MAA 不认这个锁，所以写之前必须先关掉 MAA。
  - MAA 会在定时触发前 2 分钟切换配置并重启界面。所以从关闭 MAA 到重开完成，整段时间都要避开每个定时触发前 2 分钟起的窗口。
  - 如果 MAA 已经关闭、又没有锁，说明用户可能正在操作。这时先不写，告诉用户，等用户确认自己没在操作后才写。`maa-setup` 第一次写连接设置时通常就是这种情况，同样先确认。
- 写入脚本拒绝打开任何与源石、抽卡、礼包、付费、登录相关的设置。理智药数量只接受当次授权的值。
- 读配置时只输出白名单摘要，不输出整份配置、连接地址、凭据或账号标识。
- 05 的实现先开放已存在的普通队列启停/重排、原生定时槽和定时提醒；拒绝未知字段、新建任务、登录启动入口及无限量临期药。启用任务或定时时检查间接消耗，不能借已有值绕过安全边界。摘要用配置序号代替私人名称，备份和待执行/结果记录保存在私有目录。
- 配置维护预留 120 秒关停至重开的预算（正常关停最多 30 秒、重开最多 60 秒），覆盖所有每日与单次定时前两分钟至触发分钟结束，按本机时区判断，阶段间重新检查。超时或未能证明全窗口安全时保留未知结果。重开使用已核的 MAA 原生 `--skip-startup-auto-run`，跳过自动启动连接目标和任务，不改变保存设置；没有可正常关闭的主窗口时交用户处理，不强杀。
- 读取摘要提供 revision 指纹，请求绑定该版本；关停后再次绑定目标任务、队列或定时槽的对象快照，以及决定定时目标的当前配置、模式和队列，变化则核对而不重放下标。队列重排按原位置排列，允许同类型任务重复。药剂授权作为本次总上限，每个任务按所属配置的单次定时次数计算（明确分配至少计一次），最后跨配置求和；无限每日重复不能消费一次有限授权。药剂字段服从已核的 MAA 32 位有符号整数范围。

### 检查与修法

- 有一套共享的检查库，每个检查配一个修法。
  - `maa-setup` 按安装顺序走一遍：检查，没通过就执行修法。用户发起安装，就等于同意了这些安装步骤，但下载前仍要先问。
  - `maa-doctor` 按症状随时诊断，每项修法都先问用户。
- `maa-doctor` 的流程参照 Claude Code 的 `/doctor`：
  - 先只读诊断，报告结果；
  - 每项修法都先问用户，同意了才执行；
  - 不提供「全部修复」，但用户可以一次点名批准多项。
- 检查分为这几组：
  - 安装：MAA 目录与版本、Node、设置文件、私有目录；
  - 连接：adb、模拟器、端口；
  - 配置：能否解析、本项目写入的字段是否合法、定时；
  - 写入锁：持有者是否还在运行、有没有遗留锁；
  - 凭据：有没有、是否过期，不打印值；
  - 私有文件；
  - skill 安装：版本是否最新、目录联接是否完好；
  - MAA 自身问题：只转介。
- 每条结果包含状态（正常、提醒、错误）、一句原因、一条修法，以及修法类别：由 skill 来修，或只能用户手动修。
- 输出分给人读和给程序读两种。给程序读的输出带退出码：0 表示正常，1 表示有错误，2 表示意外失败。
- 知识范围：第一版只覆盖本项目 skill 范围内的问题。问题出在 MAA 自身时（例如识别失败、MAA 的缺陷、模拟器兼容问题、游戏更新后 MAA 还没适配）就转介：给出 MAA 官方文档、常见问题和 issue 的入口，附上去掉账号信息的日志摘要。
- 读 MAA 日志时，按 MAA 的结构化回调（连接信息、任务链错误、子任务错误）判断失败类型，不只靠关键字。进程退出码为 0 不代表成功。

### 账号快照与建议报告

- 扫描用 MaaCore 自带的仓库识别和干员识别。识别由用户在 MAA 界面里启动（skill 不操作设备），skill 读取识别结果。
- 森空岛作为第二来源，不需要开模拟器。
- 账号快照直接用共享工具的输入格式，不另起一种。11 建立共享 `AccountSnapshot`：保留 MAA 原扫描时间与实际读取时间、已识别的 operators/items 和各域状态，未知练度及未读库存不补零；空完成结果标为部分。输入只读结构化回调 JSON 或 GUI 本地识别缓存，其他来源不伪装成本地识别。保存只写私有目录的账号快照，使用独占互斥和原子替换，未完成或解析失败作为快照状态保留；模板摘要提供中文及英文，其余语言由 agent 按设置翻译。接口与源码依据见 [account 来源核对](account-sources.md)。
- 建议报告要分清已核实和推断，给出可以照着做的步骤和每一步的花费。引用资料时写明作者、日期、来源和可信度。
- 会交给 `maa-daily` 执行的建议报告，默认经过一轮独立审查：一个审查员审一次，只接受真正的错误；接受的错误改正后不再复审，报告里列出这些改动。用户调用时明确说跳过的，不审，报告标「未审查」。随口问答不审。
- 独立审查的做法：Claude Code 上用一个全新上下文的子代理；Codex 上新起一个 `codex exec` 进程，配一份自包含的说明。两边共用同一份审查说明模板。

### 日常操作

- 关卡任务：只处理用户当次明确交办的关卡。核对关卡、难度、前置条件和作业要求，按地图分批。用户点开始后，一直跟踪到出结果。
- 备选作业：
  - 准备时，每关一份主作业加若干备选，一起交用户批准。
  - 只有 MAA 明确报告该关失败或没拿到三星时，才换下一份；备选用完就停下并报告。
  - 结果未知时只核对，不换作业，也不重打。
  - 换上备选后怎么开始：优先用 MAA 自己的机制接着运行，具体用哪种方式在实现时核实。做不到时，agent 把下一份备选准备好，请用户点开始。
- 专精排程：核对受训者、技能、进度和材料；安排助手和开训后的换人；按实际完成时间设 MAA 原生的单次定时。
- 专精排程的防误判措施。它们来自一次真实故障（MAA v6.22.0：换受训干员后，培养任务回报「目标已满足」并提前结束，实际没有开训）。根因尚未证实，预入驻的做法也还没有经过实跑验收，两者都标为未验证：
  - 开训的证据：MAA 回报了训练确认（v6.22.0 日志里是 `InfrastTrainingConfirm`），目标干员、技能、档次正确，并且有倒计时。任务返回成功、全部任务完成、培养计划被自动清除、回报「目标已满足」（`AlreadySatisfied`），都不算开训。
  - 「目标已满足」和账号快照里已知的专精等级矛盾时，按失败处理：停用依赖这一档的后续单次定时，先核实游戏里的真实状态。用户已经手动开训的阶段不重放。
  - 换受训干员时拆成两次原生执行：先执行一次只领取、并让目标干员进驻训练室的基建任务（不开训、不续训），间隔 6 分钟后再执行开训任务。前一位还在训练时，预入驻可能跳过换人，所以定时执行完毕不代表目标已就位，仍按上面的证据验收。
  - MAA 的原生单次定时只存时分，没有日期。错过且仍启用的槽要停用，防止第二天同一时刻误触发。
- 只执行用户批准过的建议报告条目，或者用户当次明确说的事。

## 测试决定

- 好的测试只看外部行为：skill 做了什么（调用了哪个脚本、改了哪些键、有没有拿锁、有没有先问用户），脚本输出了什么。不测内部怎么实现。行为评测同样只看行为，不看措辞。
- 设两个测试接缝。
- **接缝一：行为评测（skill 层）**
  - 把 skill 装进临时目录，用 `claude -p` 和 `codex exec` 驱动。
  - 配一个假的环境：假的 MAA 目录和配置、账号快照，以及替代 adb 和 MAA 的桩脚本。
  - 把运行记录转成统一格式，再按规则打分。规则只看行为，例如：
    - 配置改动只碰允许的键；
    - 写入前拿了锁；
    - 没有打开源石或抽卡相关的设置；
    - 输出里没有凭据；
    - 下载前问了用户；
    - 建议报告带审查标记。
  - 每条规则配一份「应当通过」和一份「应当拦下」的样例记录，用来离线自检。
  - 改动前后用同一个模型、同一批场景比较，分数不能下降。
- **接缝二：脚本命令行（工具层）**
  - 每个共享脚本都通过命令行或导出函数来测：写入脚本与锁、检查与修法、偏好脚本、成本计算、基建技能表、作业匹配、NGA 读取、版本指纹核对。
  - 用真实的临时目录。
  - 只伪造系统边界：MAA 进程、adb、网络。MAA 进程用假进程模拟快、慢、不肯退出几种情况，用来测进程树清理。
- 版本指纹核对用固定的样例源码树来测，覆盖三种情况：没变、变了、条目缺失。
- CI 只跑离线部分：脚本测试、评分规则自检、隐私检查。真模型评测在维护者本机跑。
- 可参考的先例：
  - 维护者私有项目里 dsh 的行为评测：场景加样例记录，只看行为的规则，改动前后对比；
  - 现有 `maa-daily` 辅助脚本的单元测试：用带私密标记的样例配置，断言私密内容没有泄漏；
  - dsh-maa-cli 的假 MAA 进程测试。

## 不在范围

- maa-cli 和非 Windows 平台；国服以外的服务器。
- 自己写图像识别（直接用 MAA 自带的）。
- 修复 MAA 自身的问题（第一版只转介）。
- 任何与源石、抽卡、礼包、付费、登录相关的自动化。
- 让 agent 点击游戏或操作设备。
- 在 CI 里跑真模型评测或真机 MAA。
- 打包 MAA、游戏数据或企鹅物流数据。
- 迁移维护者的个人数据（这在私有环境里做）。

## 其他说明

- **已有的相关项目**（2026-11 查）：
  - dsh-maa-cli：DeepSeek Harness 插件，基于 maa-cli，和本项目的日常操作、账号建议高度重叠；
  - arknights-base-skill：基建排班 skill；
  - MAA-PRTS：从森空岛读 box、再匹配作业的桌面程序；
  - 企鹅物流的掉率服务。

  没有找到面向普通玩家、用 SKILL.md 驱动 MAA 图形界面版的公开 skill，也没有对应 setup、doctor、help 的 skill。

  本项目和 dsh-maa-cli 的区别：
  - 宿主：Codex 和 Claude Code；
  - 数据来源：多了森空岛、NGA、B 站；
  - 驱动方式：改 MAA 图形界面版的配置，用 MAA 原生定时；
  - 安全边界，以及审查和评测流程。
- **借鉴 dsh-maa-cli 的思路**：
  - 结构化失败分类；
  - 自定义基建排班的规则；
  - 作业匹配；
  - MAA 的已知坑，例如作业列表条目会丢失循环次数、结束进程要按进程树结束；
  - 用假 MAA 进程做测试。

  改写使用它的仓库识别和干员识别回调解析函数之前，要先在固定提交上逐字重读原代码。

  不借鉴的部分：让模型生成的计划直接设置源石或药剂；未经批准自动换作业；不固定版本的下载；用正则表达式读 TOML。
- **起点**：维护者现有的 maa-daily skill（改配置、刷关、排专精）是新 `maa-daily` 的起点，迁入时剥离个人内容。
- **共享工具的复用**：维护者的私有项目以后会改为引用本仓库的共享工具，这件事在那个项目里单独处理。
