## 问题陈述

用 MAA 的玩家希望 Codex 或 Claude Code 帮忙做这些事：
- 装好并配置 MAA；
- 弄清自己账号的家底，拿到培养和基建建议；
- 日常改配置、刷指定关卡、排专精。

2026-11 查过，还没有面向普通玩家、能做这些事的公开 skill（见「其他说明」）。

维护者自己现在的做法，散落在一个越来越大的 skill 和一份私人手册里：
- 功能越加越多。一份手册里装着授权、环境、待办、材料、经验好几类内容。
- 两个 agent 同时改 MAA 配置时，是否冲突只能看日志去推断。
- 培养和基建分析没有固定流程。
- 同一个工具在不同地方各有一份实现。

## 方案

建一个公开的 MIT 仓库，提供五个 skill，Codex 和 Claude Code 都能装：

- `maa-setup`：从零装好 MAA 和周边环境，已经做过的步骤自动跳过。
- `maa-account`：扫描账号，生成账号快照，给出培养和基建建议报告。
- `maa-daily`：日常改 MAA 配置、刷指定关卡、排专精、设单次定时。
- `maa-doctor`：诊断问题，经用户同意后修复；MAA 自身的问题转介出去。
- `maa-help`：只用文字告诉用户有哪些功能、该用哪个 skill、怎么安装，自己不做任何操作。

另有一个共享脚本目录 `maa-core`，供四个操作类 skill 调用，不是面向用户的入口。

几条总原则：
- 每个 skill 按「能写什么」划定边界。
- 用户数据全部放在仓库外的私有目录。
- 安全边界写死；其中碎石和临期药在用户当次批准后可用（2026-11-13 修订，见「安全边界」）。
- MAA 发新版本时，由自动核对来跟踪。

## 用户故事

### 安装与上手

1. 作为第一次用 MAA 的玩家，我想让 agent 一步步带我装好 MAA、模拟器和 adb，这样我不用自己翻文档。
2. 作为玩家，我想每一步都先检查再动手，已经做过的自动跳过，这样重复运行安装也不会弄乱已经配好的东西。
3. 作为玩家，我想每次下载程序前都能看到文件名、来源和大小，由我决定是否下载，这样不会下到来路不明的文件。
4. 作为玩家，我想 agent 只给官方来源的下载链接，这样不会装到被篡改的版本。
5. 作为玩家，我想 agent 帮我找到模拟器的 adb 地址并测试连接，这样 MAA 能连上。
6. 作为玩家，我想 NGA、森空岛、B 站的凭据由我自己在脚本里输入，agent 只检查设了没有，这样凭据不会出现在对话里。
7. 作为玩家，我想安装时只被问一次偏好语言，之后操作类 skill 的回复和报告都用这个语言，这样我不用每次都说明。（2026-11-11 修订：`maa-help` 只提供文字帮助，按我当时说话的语言回复。）
8. 作为玩家，我想安装时定下私有目录的位置（默认放在用户目录下），这样我的数据不会混到别的地方。
9. 作为玩家，我想 agent 检查我的 Node 版本够不够，这样共享工具能运行。
10. 作为玩家，我想安装时就知道 B 站相关功能是实验性的，这样我不会依赖它。
11. 作为 Claude Code 用户，我想通过插件市场从 GitHub 安装这套 skill，这样安装和更新都走 Claude Code 自带的流程。

27. 作为玩家，我想让 agent 改 MAA 的日常队列、基建排班、定时和提醒，这样我不用在界面里一项项点。
28. 作为玩家，我想每次改配置前先备份，只改必要的项，改完重开 MAA 并读回核对，这样出了错也能恢复。

31. 作为玩家，我想写入避开 MAA 定时触发前的那段时间，这样定时不会被错过。

34. 作为玩家，我想在结果未知时（比如中途断连），agent 先核对而不是直接重打，这样不会白花理智，也不会重复操作。
35. 作为玩家，我想 agent 及时报告失败、未三星、理智不足和明确超时，这样我能及时处理。
36. 作为玩家，我想 agent 按我批准的内容排专精：受训干员和技能来自建议报告或我当次说的话，agent 负责安排助手、算好时间、设好 MAA 原生的单次定时。这样专精能一个接一个地进行。
37. 作为玩家，我想 agent 只执行我批准过的建议报告条目，或者我当次明确说的事，这样不会出现我没同意的改动。
38. 作为玩家，我想理智药只在我当次给出数量时才用，这样理智药不会被意外用掉。（2026-11-13 修订：碎石和理智药一样，只在我当次批准并给出数量时才用。临期药没有数量可给，我当次批准的是「用临期药」这一策略和临期天数。两者由工单 27 交付，在此之前脚本仍然拒绝。）

55. 作为玩家，我想 README 清楚写明免责声明：这是非官方项目，自动化可能违反游戏协议，自行修改后果自负。这样我在使用前就清楚风险。

### MAA 版本跟踪

56. 作为维护者，我想依赖的每条 MAA 行为都有源码指纹，这样 MAA 一改就能被发现。
57. 作为维护者，我想 MAA 发正式版后自动核对：没变就自动开 PR，把版本加进「源码已核」；变了就开 issue。这样我不用每次都手动对照源码。
58. 作为维护者，我想 MAA 发 beta 时也核对，有变化就开提前预警 issue，这样能赶在正式版之前改好 skill。
59. 作为玩家，我想知道当前 skill 在哪些 MAA 版本上源码已核、实机已核，这样我知道该不该升级。
60. 作为玩家，我想在未核实的 MAA 版本上收到提醒，但仍然可以继续使用，这样升级 MAA 后 skill 不会突然用不了。

### 维护与发布

61. 作为维护者，我想 main 只能通过 PR 合并，这样每个改动都有记录。
62. 作为维护者，我想每次发布前跑改动前后的行为评测，并且分数不能下降，这样改动不会让 skill 变差。
63. 作为维护者，我想 CI 只跑离线检查（单元测试、评分规则自检、隐私检查），真模型评测在我本机跑，这样公开 CI 里不用放模型账号的凭据。
64. 作为维护者，我想每个 PR 都过隐私检查，这样个人路径和账号信息不会进入公开仓库。
65. 作为维护者，我想用语义化版本号发布，附更新记录，插件版本号也同步更新，这样用户一看版本号就知道改动有多大。
66. 作为维护者，我想开发时 Codex 和 Claude 直接用本地 clone 里的 skill，这样一改就能试，`git status` 一看就知道改了什么。
67. 作为维护者，我想每张实现工单都能交给 Codex 或 Claude 独立完成，这样工作可以并行。
68. 作为外部贡献者，我想通过 GitHub Issues 报告问题，通过 PR 贡献代码，这样我能参与改进。
69. 作为被借鉴项目的作者，我想在 README 和第三方声明里看到致谢和许可声明，这样我的工作得到承认，许可条件也得到遵守。
70. 作为维护者，我想我的私有项目以后能直接复用这里的共享工具，这样每个工具只用维护一份。

## 实现决定

### 仓库与打包

- 公开仓库，采用 MIT 许可证。
- 不打包 MAA 的代码和资源，也不打包游戏数据、一图流数据和企鹅物流数据，用的时候再取：
  - MAA 的数据从用户本机读取；
  - 中文游戏数据表从公开的游戏数据镜像按固定提交读取，实现时写明是哪个仓库，并注明出处；
  - 材料价值来自一图流；
  - 掉率来自企鹅物流。
- 每个 skill 一个目录，入口是 SKILL.md，旁边放参考文件和脚本。
- 同一套目录结构，既能用 Claude Code 插件市场安装，也能用 Codex 的 skill-installer 安装。仓库根目录放 Claude 插件和插件市场的描述文件。
- 两种安装方式都是原样复制目录，所以 SKILL.md 要写成两个宿主通用。宿主之间的差异（比如独立审查怎么发起）写在一份宿主说明参考文件里。不另写复制安装脚本。
- 共享脚本集中在 `skills/maa-core/`。它不是操作入口，但带一份 `SKILL.md`，因为 Codex 的安装器要求每个被安装的目录都有。操作类 skill（setup、account、daily、doctor）通过相邻目录 `../maa-core/scripts/` 调用，每个脚本只有这一份实现。
- 操作类 skill 开始前先确认相邻的 `maa-core` 存在。缺失时不继续操作，按宿主告诉用户怎么补装；这段指引写在每个操作类 skill 自己的 SKILL.md 里，因为此时 `maa-core` 里的文件读不到。
- 维护者开发时，用目录联接把两个宿主的 skill 目录指向本地 clone。
- skill 正文用中文。README 以中文为主，开头附英文简介。
- 只支持 Windows 上的 MAA 图形界面版，服务器只支持国服。
- 共享工具需要 Node 24，直接运行 TypeScript 源码。

### 五个 skill 和边界

| skill | 读 | 写 | 不写 |
| --- | --- | --- | --- |
| `maa-setup` | 环境、MAA、模拟器 | 设置文件（经偏好脚本）、私有目录骨架、环境记录、MAA 配置里的连接类设置（经写入脚本） | 账号快照、报告 |
| `maa-account` | 游戏（经 MAA 识别）、森空岛、社区资料、私有目录 | 账号快照、建议报告 | MAA 配置 |
| `maa-daily` | 私有目录、建议报告、MAA 配置和日志 | MAA 配置（经写入脚本）、待执行和运行记录 | 账号快照、报告 |
| `maa-doctor` | 以上全部 | 最近一次检查的记录；用户同意某项修法后，经对应的写入通道修复 | 不另开自己的写入通道 |
| `maa-help` | skill 说明 | 无。只用文字回答，不运行脚本 | 一切 |

- 专精：「专哪个技能」属于建议，归 `maa-account`；「什么时候开训、选谁当助手、设定时」属于操作，归 `maa-daily`。
- 基建：「怎么排」属于建议；「写进 MAA 的自定义基建排班」属于操作。
- `maa-help` 只提供文字帮助：有哪些功能、某个需求该用哪个 skill、怎么安装。用户在 help 里要求改偏好时，help 说明由哪个操作类 skill 记录，自己不写。
- 四个操作类 skill 都可以做两件事：
  - 经偏好脚本改结构化设置，例如用户说「以后用英文」；
  - 把用户新的偏好原话追加进偏好原话文件，但不能改写旧条目。
- 调研工具（NGA、森空岛社区、B 站、作业站）属于共享工具层，不单独做成 skill。

### 私有目录与设置文件

- 设置文件固定放在 `%USERPROFILE%\.maa-skills\config.json`，记录语言、私有目录、MAA 目录和服务器。环境变量 `MAA_SKILLS_HOME` 可以改变它的位置，评测时就靠它指向临时目录。
- 设置文件只由偏好脚本写入：先写临时文件，再改名替换。
- 私有目录里按写入者分文件：
  - 偏好原话：四个操作类 skill 都可以追加；
  - 环境记录：`maa-setup`；
  - 账号快照和建议报告：`maa-account`；
  - 待执行和运行记录：`maa-daily`；
  - 最近一次检查的记录：`maa-doctor`。
  - 凭据：只由用户本人在自己的终端运行的输入脚本写入（`maa-setup` 给出命令）；读取器只记下实际读取的结果。设置文件不记录凭据，凭据的位置由私有目录决定。撤销由用户删除对应的 `<服务>.json` 和 `<服务>.status.json`，agent 不代删。（2026-11-13 补充，由工单 09 交付）
- 通用经验（某个 MAA 版本的行为、游戏机制）写进 skill 的参考文件，随仓库走。只对某个用户成立的约定，放进这个用户的私有目录。
- 每个操作类 skill 开始时先读设置文件，按其中的语言回复和写报告。没设语言时，按用户第一句话的语言回复，并提示可以设置。`maa-help` 不读设置文件，按用户这句话的语言回复。

### MAA 配置写入

- 对 MAA 配置的所有改动都经过同一个写入脚本，在一个进程里依次完成：
  1. 确认现在可以写；
  2. 获取写入锁；
  3. 关闭 MAA；
  4. 备份；
  5. 只改必要的键；
  6. 重开 MAA；
  7. 读回核对；
  8. 记录改了哪些键；
  9. 释放锁。
- 写入锁以独占方式创建。锁里记录 skill、宿主、脚本进程号、开始时间和当前步骤。

  - MAA 会在定时触发前 2 分钟切换配置并重启界面。所以从关闭 MAA 到重开完成，整段时间都要避开每个定时触发前 2 分钟起的窗口。
  - 如果 MAA 已经关闭、又没有锁，说明用户可能正在操作。这时先不写，告诉用户，等用户确认自己没在操作后才写。`maa-setup` 第一次写连接设置时通常就是这种情况，同样先确认。

- 任务身份同时核对原生 `$type` 与 `TaskType`，缺失、未知或不一致的任务摘要为 OtherTask，不据标签授权启用、药剂或定时激活；重排只接受整队类型对应一致的普通任务，包括已停用条目。仅 `Timers.List` 中现有槽省略的 `IsEnabled` 按原生 null 单次处理，可明确修改；其省略/null 在窗口、药剂次数、关停绑定及重开读回中等价，其他字段漂移仍失败。revision 保留原始 JSON 的区别，备份保留原始字节。

- 批准后的碎石与临期药（2026-11-13 修订，由工单 27 交付；27 完成之前，写入脚本、skill 和评分规则仍按上面的旧规则拒绝这两类设置）：
  - 碎石（用源石恢复理智）：只在用户当次请求里批准并给出数量时写入。这个数量是本次总上限，核对方式和理智药相同：每个任务按所属配置的单次定时次数计算，再跨配置求和；有限的碎石数量不能由每日重复的定时消费。固定的 MAA v6.21.4 读入配置时，`UseStoneAllowSave` 不为 true 就把 `UseStone` 重置为 false，所以写入器把这两个字段一起写，并在读回时一起核对。2026-11-13 补充：写进配置的数量会留在那里，之后每次运行这个任务，MAA 都按这个数量重新生效，所以「本次总上限」只对写入时核对过的那几次运行成立。理智药的数量也一样。再运行之前怎样处理，见下面「剩余数量」一条。
  - 临期药：MAA 没有临期药的数量字段，所以用户当次批准的是「用临期药」这一策略和临期天数（MAA 界面的范围是 1–30 天，默认 2 天）。开启后，即使理智药的数量授权已经用完，MAA 仍会继续使用临期天数内的药，数量授权约束不了临期药。批准写入后，这项设置可以留在配置里，包括留在每日重复的定时上。`UseExpireMedicineForActivity`（活动结束前吃当周过期的理智药）属于同一类，要在批准里单独点名。2026-11-13 补充：临期药的批准可以和已批准的作业计划或专精计划放在同一次写入请求里，同样要是当次批准；理智药和碎石的数量授权仍然不能和这两种计划同请求。带专精计划的定时写入会运行到开着临期药的 Fight 任务、却没有带临期药批准时，写入器在访问进程之前拒绝，并给出单独的原因。作业计划的写入只改自动战斗的作业列表，不启用任务或定时，不受这项检查约束。
  - 已有的值：要启用的任务或定时，其 Fight 任务上已经开着碎石或临期药时，仍然要有当次对应的批准才能启用，不能借已有值绕过。读取摘要列出每个 Fight 任务当前的理智药、碎石和临期药状态，让用户知情后再批准。
  - 偏好原话和已批准的报告条目不能代替当次批准，这一点碎石、临期药和理智药相同。
  - 关闭（2026-11-13 补充）：把碎石或临期药的开关改为 false，只需要普通的当次请求，不需要数量或天数。
  - 剩余数量（2026-11-13 补充，由工单 27 交付）：这一条管的是数量来自 Fight 任务字段、并且经数量授权写入的运行，也就是日常队列和它的定时。这样一次运行结束、失败或被中断之后，它已经用掉的理智药和碎石算在同一次批准里，再运行只能用剩下的数量，或者由用户重新批准。写剩余数量是一次普通的当次写入，在请求里引用原来的批准原话，数量等于剩余数；原来的批准不在当前对话里时（例如宿主重启之后）算历史授权，要重新批准。剩余数为 0 时这次批准已经用完：模型要么把理智药或碎石的开关关掉、不带它再运行，要么停下告诉用户。用掉多少读不到时按未知处理：停下告诉用户，不重试，也不写一个猜出来的剩余数。目前没有工单交付日常队列运行的用量读取，所以在有工单交付之前，这类运行的用量一律是未知。
  - 抽卡、礼包、付费、登录的拒绝不变：Award 任务的 `FreeGacha`、`SpecialAccess`，以及 StartUp 等登录启动入口，任何批准或偏好都不能打开。
  - 批准由 agent 在写入请求里声明（`authorization.source` 加 `reference`）。脚本核对的是内容和状态（revision 指纹、目标快照、数量和天数），不核对批准人的身份。

### 检查与修法

- 有一套共享的检查库，每个检查配一个修法。
  - `maa-setup` 按安装顺序走一遍：检查，没通过就执行修法。用户发起安装，就等于同意了这些安装步骤，但下载前仍要先问。
  - `maa-doctor` 按症状随时诊断，每项修法都先问用户。
- `maa-doctor` 的流程参照 Claude Code 的 `/doctor`：
  - 先只读诊断，报告结果；
  - 每项修法都先问用户，同意了才执行；
  - 不提供「全部修复」，但用户可以一次点名批准多项。
- 检查分为这几组：
  - 安装：MAA 目录与版本、Node、设置文件、私有目录；
  - 连接：adb、模拟器、端口；
  - 配置：能否解析、本项目写入的字段是否合法、定时；
  - 写入锁：持有者是否还在运行、有没有遗留锁；
  - 凭据：有没有、是否过期，不打印值；
  - 私有文件；
  - skill 安装：版本是否最新、目录联接是否完好；
  - MAA 自身问题：只转介。
- 每条结果包含状态（正常、提醒、错误）、一句原因、一条修法，以及修法类别：由 skill 来修，或只能用户手动修。
- 06 先贯通配置解析与遗留写入核对。最近检查仅保存脱敏结果与时间。核对绑定最新关联备份、唯一最新待执行记录、持有者、完整当前配置和 MAA 状态；证据变化则重新诊断。普通单配置事务只在当前配置与备份/预期结果精确一致时提供修法；损坏、部分变化或带未支持作业/训练资源的事务保留证据。清锁与恢复是同一事务的互斥选项，每项点名批准；配置已生效但 MAA 关闭时不声称重开完成。恢复先私有归档，再把原改动字段反向请求交原写入器，历史药剂授权不替代当次授权。并发恢复用独占短期互斥，未知互斥也不直接删除。
- 输出分给人读和给程序读两种。给程序读的输出带退出码：0 表示正常，1 表示有错误，2 表示意外失败。
- 07 接入已存在环境：setup 只读现场检查，首次经偏好脚本设置语言和私有目录，骨架仅创建目录与脱敏环境记录。adb 从已记录路径、MAA／模拟器相邻目录、PATH 与用户输入发现；本票自动测试只接收本机 loopback 地址和 emulator 编号，远端地址交用户手动核对。多候选先选，显式输入可缩小范围，发现指纹变化重新选择；只运行 devices、connect、指定设备 get-state，不操作设备。连接配置仅开放当前配置已有的 AdbPath／Address／AutoDetect／AlwaysAutoDetect，保留其他字段；关闭确认、锁、维护窗口和未知结果规则不变，doctor 可核对该单配置事务。缺失程序只给官方入口，下载由 08 交付。验证版本记录目前为空，不登记起点历史为本仓库实机验证。
- 知识范围：第一版只覆盖本项目 skill 范围内的问题。问题出在 MAA 自身时（例如识别失败、MAA 的缺陷、模拟器兼容问题、游戏更新后 MAA 还没适配）就转介：给出 MAA 官方文档、常见问题和 issue 的入口，附上去掉账号信息的日志摘要。2026-11-13 修订：先查明原因，再判断是否属于这一类，见下面「环境类失败」一条。
- 07 接入即使连接字段一致，也须检查遗留事务锁；active／stale／unknown 不返回接入完成，重开失败后交 doctor 核对。普通配置 writer 不接受连接字段；setup 专用入口在 writer 内重新选择与复测，按当前配置生成精确四字段差异，不接受任意 changes 或其他授权 grant。恢复原空／相对路径和开关仅限已核遗留事务。损坏／不可读设置给具体原因、修法及执行者，保留原字节并继续独立检查，不当成首次设置、不猜未知私有目录。
- 09 凭据（2026-11-13，由工单 09 交付）：NGA、森空岛账号和实验性 B 站的凭据只由用户本人在自己的终端运行 `credentials.ts input` 输入；标准输入不是终端时拒绝，只有加 `--stdin` 才从标准输入逐行读取答案，这个参数只用于自动测试和用户自己的脚本。agent 不运行 `input`，也不加 `--stdin`；不在对话里索取、复述或保存凭据，也不替用户登录。每个服务只收一个值（NGA 的 Cookie 请求头、森空岛 token、B 站 SESSDATA），单值最多 8192 字符，没有密码输入项；先要保存过设置文件。值按 Windows 当前用户（DPAPI）加密存放在私有目录，非 Windows 不保存；取消或失败不动原有记录。撤销时由用户自己删除私有目录 `credentials/` 下对应服务的 `<服务>.json` 和 `<服务>.status.json`，agent 不代为删除。setup 与 doctor 共用同一个只读检查：不解密、不联网，状态分未设置（正常）、尚未验证（提醒）、可用（正常）、已知过期和无法读取（错误），设置不可读时位置未知（提醒）。「可用」只来自当前这份值的实际读取结果，不按时间自动降级；重新输入后回到尚未验证。凭据修法都由用户做，doctor 即使收到点名批准也返回 `user-manual-repair`。森空岛粘贴前用用户的语言给出两点知情说明；输入流程的说明文字有中文和英文，其他语言用英文。
- 读 MAA 日志时，按 MAA 的结构化回调（连接信息、任务链错误、子任务错误）判断失败类型，不只靠关键字。进程退出码为 0 不代表成功。
- 环境类失败（2026-11-13 修订，由工单 10、16、17 交付）：连接断开、模拟器或游戏客户端异常、MAA 进程异常、识别环境不对（例如分辨率不符、界面被遮挡）这类失败，先查明原因并核对当前状态，再由模型决定下一步：在原有批准范围内重试、换下一份已批准的备选，或者停下告诉用户。环境类失败不算作业失败：当前作业不记为已失败，也不因此自动换下一份。重试和换作业都不增加理智药或碎石的授权数量，启动方式也不变（用户点开始，或 MAA 自己的机制）。2026-11-13 补充：数量来自 Fight 任务字段、经数量授权写入的运行（日常队列和它的定时）结束、失败或被中断之后，已经用掉的理智药和碎石算在同一次批准里，再运行只用剩余数量或重新批准，用掉多少读不到就停下告诉用户；这一条由工单 27 交付，规则见「MAA 配置写入」的「剩余数量」。指定关卡的批次经 MAA 的自动战斗运行，没有理智药数量也没有碎石，本项目不为它授予数量；发现批次用了没有经本项目批准的理智药时，运行记录写明并告诉用户，模型不自行重试或换作业，这一条由工单 16、17 交付，见「日常操作」。查明原因后结果仍然未知的，照旧只核对、不重放。查明是 MAA 自身的问题时，照旧转介。

- 建议报告要分清已核实和推断，给出可以照着做的步骤和每一步的花费。引用资料时写明作者、日期、来源和可信度。

### 日常操作

- 关卡任务：只处理用户当次明确交办的关卡。核对关卡、难度、前置条件和作业要求，按地图分批。用户点开始后，一直跟踪到出结果。

- 29 匹配改进（2026-11-13 补充，由工单 29 交付；核对见[作业接口核对](stage-jobs-sources.md)）：没写 `requirements`（缺省、null 或空对象）的干员条目记为「要求未写明，待核」，不凭持有判满足；MAA v6.21.4 对这类条目不作要求，也没有可依据的按稀有度默认值，所以不给推定值。只有一个位置的成员全部未持有、写明了可读的要求，且其他位置全部核对通过时，候选标为需借助战（support）：不进默认的主作业和备选，单独列出缺的位置和要求；批准时用户逐份点名（`supportJobs`）才能准备，待执行记录写明借的位置。持久的 SupportMode 不改，开始前由用户在自动战斗页勾选「借助战」并选「补漏」；MAA 借助战只按名字和技能挑人，助战练度由用户确认。评分取自作业站查询摘要，只调整建议顺序：作业站标记评分足够且好评率达到门槛的在前，评分不足或未知其次，好评率低的最后，同档保持接口顺序；门槛随票数升高，5 票 65%，按票数的对数过渡到 100 票 85%，100 票以上不再提高，不足 5 票不设好评率门槛；评分不改变状态、要求核对或批准。动作引用了没有在 opers、groups 声明的干员或无法识别的名字时，作业记为待核并列出名字；群组名、群组成员、固定游戏表里的召唤物和装置、本作业用设置单位坐标登记的单位不算。作业写的关卡（stage_name）按 MAA v6.21.4 的方式解析：与关卡表某一关的 stageId、代号、levelId 或名称完全相同（区分大小写）才算指向它，levelId 按 MAA 地图数据的写法用全小写比较，关卡表里大小写混合的写法和 levelId 末段都不算；只指向所选关卡或它同一 levelId、同代号、同难度组、一个普通一个突袭的孪生关卡时才算本关，指向同一张地图上的其他难度组、其他模式（例如 `#s`）或同难度的另一关（例如活动任务关卡的 `_m1`/`_m2`）时记为无法证明，指向别的地图时记为其他关卡，对应不到或对应到多处且混有其他关卡时无法确定；后三种都不能准备。这一条取代 15 的「非 NONE 组须作业明确 stageId」和 levelId 末段别名：第 9 章突袭可以用写普通 stageId 的作业，act50side_ex01/ex02 这类交换了 levelId 的关卡不再错配。作业没写难度或写 0 时，按 MAA 图形界面的处理只算普通，突袭不用。每关检索记录本次返回的作业 ID，报告区分「接口没有返回作业」「返回的都属于其他关卡」「同一张地图的其他难度组或模式，无法证明适用」「疑似退回关键字搜索、结果与这一关无关」「三页读完仍没有属于这一关的作业」「关卡名对应不到唯一的关卡」；只有前两种可以说这一关在本次检索条件下没有作业，其余写明不能据此判断没有作业。固定关卡表里 `#s`（SIX_STAR）关卡没有对应的作业难度位，列出但不匹配。匹配结果结构变化后报告指纹随之变化，旧报告上的批准不沿用。

## 测试决定

- 好的测试只看外部行为：skill 做了什么（调用了哪个脚本、改了哪些键、有没有拿锁、有没有先问用户），脚本输出了什么。不测内部怎么实现。行为评测同样只看行为，不看措辞。
- 设两个测试接缝。
- **接缝一：行为评测（skill 层）**
  - 把 skill 装进临时目录，用 `claude -p` 和 `codex exec` 驱动。
  - 配一个假的环境：假的 MAA 目录和配置、账号快照，以及替代 adb 和 MAA 的桩脚本。
  - 把运行记录转成统一格式，再按规则打分。规则只看行为，例如：
    - 配置改动只碰允许的键；
    - 写入前拿了锁；
    - 没有打开抽卡等禁止的设置，也没有在缺少当次批准时打开碎石或临期药（2026-11-13 修订；评分规则由工单 27 修改，在此之前仍把任何打开源石设置的改动判为违规）；
    - 输出里没有凭据；
    - 下载前问了用户；
    - 建议报告带审查标记。
  - 每条规则配一份「应当通过」和一份「应当拦下」的样例记录，用来离线自检。
  - 改动前后用同一个模型、同一批场景比较，分数不能下降。
  - 真模型评测怎样登录（2026-11-13 补充，由工单 28 交付；交付之前运行器仍只转发评测专用的 API key）：
    - 默认用维护者的 Claude 和 ChatGPT 套餐登录，不用 API key；API key 认证保留为可选，要用时显式指定。
    - 登录状态放在两个专用、持久的登录目录里，两个宿主各一个，在仓库、临时 home 和工作区之外，不和私有目录混放（私有目录按产品自己的设置文件定位，只比较路径）；运行器和维护者不往里面放登录以外的东西（读保护检查的合成哨兵文件除外，检查一结束就删掉，启动场景之前确认已经不在），宿主自己往里写了什么在第一次真实运行时列出来（核实后采用）；每次运行的清理不删它们。只有用户自己登录，agent 不输入凭据，运行器不复制也不读取用户日常使用的登录文件。
    - `claude -p` 不带 `--bare`（bare 模式不读取登录）。记忆文件、自动记忆、hook、插件、宿主自带的 skill、自定义命令、子代理、MCP 服务器、会话持久化和内置工具集改由专用配置目录和显式开关隔离，被测模型能用的工具只有运行器允许列表里的读文件工具和场景声明的命令，待测 skill 由运行器显式装入。真实运行出现清单之外的加载项或工具时，这次运行记为 `unverified`，不当作基线。每次升级宿主 CLI 后重新核实，`-p` 读不了已保存的登录时 Claude 一侧记为未验证，交回维护者决定。带和不带 `--bare` 的记录不可比。
    - 用套餐登录的运行，子进程环境里没有该宿主的 API key 变量；认证预检发现有就停下整批。
    - 同一个宿主的场景串行运行；登录文件不在批次之间从备份恢复。
    - 登录目录和其中的内容不进运行记录、日志和产物；被测模型读不到登录目录，做不到的宿主不用套餐登录运行。每个宿主上，读保护检查通过之前，不用套餐登录运行任何模型可以用工具的场景，首批试运行也一样，只允许认证预检那一次不带工具的最小请求（怎样不带工具，逐个宿主核实后采用；做不到的宿主，认证预检不发模型请求，第一次模型调用就是读保护检查本身）；检查用登录目录里的合成哨兵文件，不用真实的登录文件，宿主的记录里文件工具和命令两次读取尝试都在并且都被拒绝或失败、哨兵的值不在输出里才算通过，少了任何一次尝试算没有通过，检查一结束就删掉哨兵文件。
    - 撞到套餐用量上限是单独的 `unverified` 原因并中止整批，不算场景失败；批次可以续跑，已完成的场景不重跑，续跑时指纹要和原批次一致。
    - 模型用各家当前名单里的完整 id；实际使用的 id 和 token 用量从宿主输出里记录，宿主没有报告时记为未知。第一批真实运行先做小规模试运行，量出用量和耗时之后再跑完整批次。
    - 公开 CI 不变：不启动真实模型，不持有凭据。
- **接缝二：脚本命令行（工具层）**
  - 每个共享脚本都通过命令行或导出函数来测：写入脚本与锁、检查与修法、偏好脚本、成本计算、基建技能表、作业匹配、NGA 读取、版本指纹核对。
  - 用真实的临时目录。
  - 只伪造系统边界：MAA 进程、adb、网络。MAA 进程用假进程模拟快、慢、不肯退出几种情况，用来测进程树清理。
  - 原生合成 GUI 测试（2026-11-13 补充）：每一步用产品自己的时间预算，不另设更紧的测试预算。启动 60 秒、关停 30 秒用产品默认值；配置写入命令给 150 秒，即写入自身 120 秒的维护预算，加上关停前后的观察和进程启动；测试总时限取各步上限之和，为 315 秒。理由：每次原生观察或请求都新起一个 PowerShell 辅助进程，CPU 繁忙时每次要几秒，比产品更紧的测试预算会让行为正确的产品超时。证据见[诊断记录](diagnostics/2026-11-13-maa-process-close-timeout.md)。
- 版本指纹核对用固定的样例源码树来测，覆盖三种情况：没变、变了、条目缺失。
- CI 只跑离线部分：脚本测试、评分规则自检、隐私检查。真模型评测在维护者本机跑。
- 可参考的先例：
  - 维护者私有项目里 dsh 的行为评测：场景加样例记录，只看行为的规则，改动前后对比；
  - 现有 `maa-daily` 辅助脚本的单元测试：用带私密标记的样例配置，断言私密内容没有泄漏；
  - dsh-maa-cli 的假 MAA 进程测试。

## 不在范围

- maa-cli 和非 Windows 平台；国服以外的服务器。
- 自己写图像识别（默认直接用 MAA 自带的）。2026-11-13 修订：不再一律排除，确有必要时可以另加，由一张写明缺口的工单提出。
- 修复 MAA 自身的问题（第一版只转介）。
- 任何与抽卡、礼包、付费、登录相关的自动化，以及碎石以外的源石用途。2026-11-13 修订：碎石在用户当次批准后可用，见「安全边界」。
- 让 agent 点击游戏或操作设备。
- 在 CI 里跑真模型评测或真机 MAA。
- 打包 MAA、游戏数据或企鹅物流数据。
- 迁移维护者的个人数据（这在私有环境里做）。
