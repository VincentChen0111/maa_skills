# maa-core 与纯文字 help 审查

日期：2026-11-11。基点 `1566db4`，范围为提交 `49967b8`（实现）和 `57e10e3`（第一轮修复）。本包没有单独的工单：它执行维护者 2026-11-11 的三条决定（help 只提供文字帮助；共享脚本移到 maa-core、缺失时指引安装；加入专精排程的防误判措施），来源登记在规格的两张来源表。

每轮由一名新上下文的独立审查员读取自包含说明、AGENTS.md、CONTRIBUTING.md、规格相关章节和 diff；第二轮只审修复。意见由协调者逐条判断，只接受真实错误。

## 第一轮

结论：不通过，范围很窄。

| 意见 | 处置 | 理由 |
| --- | --- | --- |
| P2：`core-language`、`core-append` 期望一次 `read` 调用，但 maa-core 的说明没有要求调用方先 `read`，照说明操作的模型会被判失败；提示让 maa-core 直接处理用户请求，与它的定位矛盾 | 接受 | 工单 26 的基线会运行这两个场景，失败或不稳定会阻止发布 |
| P3：规格「偏好原话：任何 skill 都可以追加」、用户故事 7 和 50、工单 26「所有 skill 读取语言」与 help 只提供文字帮助相矛盾 | 接受 | 现行文本自相矛盾，工单 26 的这条验收无法满足 |

审查员确认无误的部分：搬迁后没有文本仍把脚本放在 maa-help；Codex 安装指引与本机安装器一致（多个路径、逐个复制、拒绝覆盖、每个路径要求 `SKILL.md`）；相邻目录在两个宿主的安装结构里都能解析；专精防误判措施与四条来源措施一致、标明未验证、不含私有内容；三条决定、`SKILL.md` 这一外部事实、「缺失时不继续操作」和 6 分钟都在两张来源表里并且归属正确；工单 26 的基线清单与场景 id 一致。

列为「不是缺陷」、未处理的几项：help 场景在模型什么都不做时也会通过机器评分（工单 26 已要求人工核对语义）；`docs/hosts.md` 仍写 help 正在工单 04 验收（本包之前就有）。
