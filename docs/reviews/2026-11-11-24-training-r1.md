### R1-1 [P2] 手动阶段完成后，后续已批准档次永远只安排观察

位置：`skills/maa-core/scripts/training-state.ts:73-74`（以及 `:103-105`）。

`manualTraining` 是当前已手动开训阶段的防重放事实，但升档时删除了当前 action/startedAt 等字段，却保留 `manualTraining=true`。因此用户要求续完 M2、当前 M1 已手动开训时，正确 M1 倒计时和完成回调虽然使记录成为 `rank=2,state=pending`，`nextTrainingAction` 仍命中手动分支，只返回 `observe`。即使按接口刷新了 M2 材料也不会安排 M2 start；观察又配置 `ContinueTraining=false`，原生任务无法替它继续下一档。

公开函数复现：`.tmp/review-probes.ts` 的 `manual-next-rank`，调用 `reconcileTraining` / `nextTrainingAction`，输出：

```json
{"probe":"manual-next-rank","state":"pending","rank":2,"manualTraining":true,"next":{"kind":"observe","dueAt":"2026-11-11T02:12:00.000Z"}}
```

依据：规格用户故事 36 要求专精一个接一个进行；日常操作要求“按实际完成时间设 MAA 原生的单次定时”，防重放仅针对“用户已经手动开训的阶段”。工单要求中断恢复与实际完成推进；训练接口第 8 步承诺完成一档刷新材料后可 apply 下一档。

建议：把手动开训事实绑定到具体档次；完成并推进后清除该阶段的 manual 标志，保留历史，下一档仍遵守材料刷新和完整开训证据。增加手动 M1 → 实际完成 → 刷新 → M2 start 的公开接缝覆盖。

### R1-2 [P2] 接受早于已知开训时间的完成回调，提前推进下一档

位置：`skills/maa-core/scripts/training-state.ts:68-74`。

完成分支仅检查 `plan.startedAt` 存在，不检查完成时间是否晚于开训/已有倒计时证据。全局时间筛选只要求不早于 action.dueAt。读取不同日志片段或遇到时钟回拨后，位于 dueAt 之后但早于本次已证实开训的 Completed 会直接改写 `target.currentRank` 并推进 rank。这不是可信的本次完成证据，且此时没有任何 issue；刷新材料后可据此安排后续档次。

公开函数复现：先读取 `01:05:01` Confirm + `01:05:10` 正确倒计时，再读取时间为 `01:05:00` 的同干员/技能/M1 Completed（dueAt 恰为 `01:05:00`）；在 `01:07` 核对返回：

```json
{"probe":"completion-before-start","startedAt":"2026-11-11T01:05:01.000Z","completionAt":"2026-11-11T01:05:00.000Z","state":"pending","rank":2,"next":{"kind":"start","dueAt":"2026-11-11T01:12:00.000Z"},"issues":[]}
```

依据：工单要求以实际开训/完成证据修正、未知先核对；来源/作者验证明确声称覆盖未来和倒序证据，现有测试只覆盖 Confirm/Countdown 的相对顺序，没有覆盖 Completed。固定 [MAA InfrastTrainingTask.cpp](https://github.com/MaaAssistantArknights/MaaAssistantArknights/blob/901e01c600f4895ac4e7e48a9b471fc9f52af301/src/MaaCore/Task/Infrast/InfrastTrainingTask.cpp) 的 Completed 是一次观察结果，不能让早于当前训练开始的观察成为本次完成依据。

建议：完成推进前校验该阶段的因果时间与已消费的最新训练观察，倒序保持待核且不升档；同时覆盖倒序完成、旧日志片段及正常完成路径。

### R1-3 [P2] 训练目标查表遗漏 patchChars，已支持的阿米娅形态无法查询或排程

位置：`skills/maa-core/scripts/training-time.ts:42-48`。

成本工具使用 `characters + patches.patchChars` 解析目标，而训练工具随后仅从 `tables.characters[cost.operator.id]` 取职业/技能/时长。因此即使共享成本已经确认目标、材料和前置条件，patchChars 中的目标也变成空对象，返回 `target-identity-incomplete` 和逐档 pending；`prepareTrainingPlan` 随后拒绝。在线 query 已加载 patches，用户补事实无法弥补这个查表遗漏。

公开函数复现：把合成目标从 characters 移到已有共享格式 `patches.patchChars`，不改目标/快照/技能表；`calculateTraining` 输出：

```json
{"probe":"patch-character","costStatus":"ok","costOperator":{"id":"char_synthetic","name":"合成干员"},"costTotal":{"materials":{"mat":3},"lmd":0,"exp":0},"status":"needs-input","role":null,"skillName":null,"issues":["training:target-identity-incomplete","training:stage-1-pending","training:stage-2-pending"]}
```

现实对应已核：批准的固定 [char_patch_table.json](https://github.com/Kengxxiao/ArknightsGameData/blob/6f63c14e27b847ef74b53b00fe51fc322b3cd7ff/zh_CN/gamedata/excel/char_patch_table.json)（Git blob `a0fc7daa64a375b8431201c7f08abe4695f9f5e7`）含 `char_1001_amiya2`（WARRIOR）和 `char_1037_amiya3`（MEDIC）；固定 character_table 只有普通阿米娅目标。此核对只读公开表，不使用真实账号。

依据：工单的明确目标、共享成本复用和按干员名查询；训练接口承诺名称有歧义时指定 operatorId，未把形态排除出目标范围。

建议：训练目标身份沿用与共享成本一致的合并目录，并以带 operatorId 的 patch 形态做公开查询/prepare 回归；避免在不同工具各自做不一致的解析。

### R1-4 [P1] 无关 Infrast 完成回调解除 start 的防重放锁定，随后能重新启用开训槽

位置：`skills/maa-core/scripts/training-state.ts:63-64`，实际重入路径经 `training-plan.ts:116-120,182-183`。

这段处理接受任意未完成 `plan.action` 的 Infrast TaskChainCompleted，没有限定 action.kind。原生 start 的任务链应是 OperProgress。若定时因另一个配置的 Infrast 任务仍在运行而错过，随后该无关 Infrast 完成，其日志时间位于本计划 dueAt 后，就会替本计划的 start 填上 completedAt。该回调没有目标身份，工具没有确认/倒计时，但状态仍保留 pending/preplaced、issues 为空；过期处理也因为 completedAt 已存在而跳过 `execution-unproven-no-replay`。重新核材料后 apply 会重新安排 start，违反结果未知不重放。

已通过完整公开 API + 真实临时 FS 验证，不仅是状态函数推测：`.tmp/review-wrong-chain.test.ts` 构造已写入的 start 意图、对应原生 null 槽、materialReady=false 及正确配置绑定，日志只含一个 Infrast TaskChainCompleted。调用 `reconcileTrainingPlan → refreshTrainingMaterials → applyTrainingPlan` 后实际输出：

```json
{"probe":"wrong-chain-full-path","reconciledState":"pending","reconciledIssues":[],"cleanup":"complete","refreshedReady":true,"reapplied":"complete","newAction":"start","timerEnabled":null}
```

所选任务/槽身份一直未变，故现有绑定检查不能拦住；新一次单次开训确实被重新启用。探针先在受限 shell 因合成记录 rename EPERM 中断，随后正常权限跑同一文件成功复现；只替代 MAA 进程边界。

依据：工单“中断或结果未知先核对，不重复开训或重复设置已生效安排”、规格安全边界及训练接口第 4/6 步。官方原生 start 走 [OperProgressProcessTask](https://github.com/MaaAssistantArknights/MaaAssistantArknights/blob/901e01c600f4895ac4e7e48a9b471fc9f52af301/src/MaaCore/Task/OperProgress/OperProgressProcessTask.cpp)，与 Infrast 链完成不同。

建议：至少把 Infrast 完成处理限定到对应的 preplace/assistant/observe 动作，不能让它结束 start；结合当前执行/任务关联保留未证实状态，普通材料刷新不能使该未知执行重新获得开训资格。补上述完整入口链路回归，以及 start 收到错误任务链和同实例无关任务日志的覆盖。
