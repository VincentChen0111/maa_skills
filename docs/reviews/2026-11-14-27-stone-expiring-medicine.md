# 27 批准后的碎石与临期药：独立审查

日期：2026-11-14。本包叠在工单 28 的提交 `d2b0edf` 上，审查范围：
- 实现：`5159fdf`…`1955143`（`5159fdf` 是先红的测试提交）；
- 第一轮修复：`0ac4c2b`、`83ebe98`；
- 第二轮修复：`f34f508`、`67d7824`。

本包开放消耗：用户当次批准后，可以用源石恢复理智、用临期理智药，所以每条路径都按安全相关审查。

审查方式：
- 每轮由一名新上下文的独立审查员审查。审查员读取自包含说明、工单 27、05、15、24、规格相关章节和 diff；第二、三轮只审修复。审查员在固定 MAA v6.21.4（`52d0b2a`）的公开源码上亲自核对过 FightTask、FightTaskUserControlModel、MedicineCounterTaskPlugin 和 tasks.json 的相关行。
- 意见由协调者逐条判断，只接受真实错误。
- 共三轮，在维护者定的上限（「轮数上限3」）之内。三轮都没有 P1、P2，没有找到不经当次批准就能碎石或用临期药的路径，也没有被拒绝的意见。

## 第一轮

结论：有条件通过，四条 P3。

审查员核对后认为以下各点正确：
- 写入、启用、定时、预算、待执行记录、doctor 恢复、专精和作业路径都经同一个谓词 `decideConsumption`，拒绝都发生在访问进程、加锁和写入之前；
- 间接消耗：启用任务、重排、改定时会运行到开着消耗的任务时，都要当次授权；
- 数量预算按定时次数累计；有限数量遇到每日定时时拒绝；
- 碎石要求 `UseStone` 和保存开关同时为真，数量大于 0；
- 59 个变异中，存活的都列在下表或判为等价。

| 意见 | 处置 | 理由 |
| --- | --- | --- |
| P3：关闭理智药时拿残留的 `MedicineCount` 和授权比较，比 05 更严，「关掉理智药」会以「数量超出」被拒 | 接受 | 有离线复现，与规格和 skill 文字不符 |
| P3：开关为 false 时，非开关字段（`UseStoneAllowSave=true`、`StoneCount`、`MedicineExpireDays`）不要授权就能写 | 接受 | 违反验收第 3 条的字段白名单；保存开关在 MAA 界面要经危险确认框才能打开 |
| P3：「开关为 null 按开启处理」等几条安全守卫没有测试，变异能通过全部测试 | 接受 | MAA 界面真的会存出 null 开关加 999 瓶理智药的状态 |
| P3：「doctor 恢复不复用原事务授权」没有测试，验证记录也说大了覆盖范围 | 接受 | 安全规则缺少回归保护 |

修复：
- 一类消耗最后关着时，只写关闭值（开关改为 false、数量改为 0）的请求只需当次请求，理智药也一样；写其他值要这一类的当次授权；
- 补测试：null 开关、计入数量的任务核对、开关与数量的合法性，以及恢复不复用原授权；
- 对应的变异都被抓到。

## 第二轮

结论：有条件通过，一条 P3。审查员确认修复后找不到不带当次授权就能消耗的路径。碎石开着时可以单独关闭理智药，不会出现理智药以 null 或 999 运行的状态（已对照固定源码的 `BuildAsstFightTask`）。

| 意见 | 处置 | 理由 |
| --- | --- | --- |
| P3：第一轮的「只能写关闭值」也套到了 doctor 的配置恢复上。撤回一次被中断的「打开临期药或碎石」时，需要一个等于事务前旧值的授权，用户没批准过，代理也看不到；锁一直留着，daily 写入被挡住 | 接受 | 有离线复现，是回归；失败方向是不写 |

修复：谓词新增消费方 `doctor-restore`。同时满足以下条件时，不需要这一类的授权：
- 只在 doctor 的 restore-config 路径上；
- 恢复后这一类仍关着；
- 每个改动值都等于最新关联备份里同一任务的值；
- 请求是当次请求。

重新打开某一类仍要当次授权。普通写入和其他消费方带 `restore` 时一律拒绝。

## 第三轮

结论：通过，没有意见。

审查员离线复现并核对了：
- 放行只能经 doctor 的 restore-config 使用最新关联备份。CLI 没有选择备份或传 `restore` 的字段；更旧的备份或与当前配置不一致的备份都得到「未知」。
- 备份本身开着这一类时仍要授权；同一次恢复里一类关回、另一类重新打开时，只要求重新打开的那一类。
- 待执行记录重放不写文件；伪造的记录不能用来打开任何一类。
- 构建者判为等价的变异 R7 确实等价：恢复写入的值都取自同一份备份。
- 第一轮的规则对普通写入保持不变。

审查员另记了两点观察，都要篡改私有目录里的备份或 MAA 配置目录里的锁才会出现。协调者判断不是缺陷，理由如下：
- 能改这些文件的一方同样能直接改 `gui.new.json`；
- 这一类始终关着，不发生消耗；
- 以后经工具打开时，要有不小于剩余数量的当次授权。
