### R1-T1 [P2] Windows 短路径让测试边界拒绝同一个合成 adb

位置：`tests/fixtures/setup-boundary.mjs:7–8,20`；同源断言位置 `tests/setup.test.ts:90,126`；烟测在 `scripts/setup-smoke.ts:42` 受影响。

固定候选的 [CI run 42918403791](https://github.com/VincentChen0111/maa_skills/actions/runs/42918403791) 中，Windows job `130186684875` 实际失败：305 总计、298 pass、6 fail、1 skip。失败包括双布局 `test` 返回 failed、公共 smoke 的 setup test 退出 1，以及两个长/短路径字节比较；一个父测试因两个子测试失败也计入 6。Ubuntu job `130186684510` 成功。审查员通过 GitHub API 独立确认了 head 对应 run 及两个 job 的结论，并阅读完整 Windows 原日志。

产品用 `fs/promises.realpath` 规范化 adb，Windows 原生实现会展开 8.3 短路径；夹具用非 native 的 `realpathSync` 处理工作区，Windows 下会保留短别名，再以 `resolve` 字符串相等检查可执行文件。CI 的 Temp 前缀是短别名；公共 smoke 的安装 core 已经原生规范化，因此其 adb 替身检查会把同一个合成 adb 的规范路径拒绝。发现仍可从显式 addresses 产生候选，connect/get-state 则失败。双布局用例的 core URL 精确匹配也使用同一非 native 规范化，有相同身份不一致；现有 CI 日志未保存它们的 hook 日志，不能断言两布局分别在哪个相等比较失败。两个导出函数断言同样错把未规范化的 fixture 路径当成唯一正确输出；CI 日志直接显示 actual 长路径、expected 等价 8.3 短路径。

本机虽不能在 D 盘创建有 8.3 别名的 fixture，审查员对已有系统程序目录短别名做了只读 Node API 对照：`realpathSync` 保留 `~`，`realpathSync.native` 与 `fs/promises.realpath` 都展开，后两者相等、前者不等。证据 `.tmp/r1-short-path-api.log`。这是确定的夹具路径身份问题，不证明产品连接失败，也不是六个独立缺陷。

CONTRIBUTING 要求完整离线入口、支持平台 CI 与实际安装验证；当前夹具在标准 Windows runner 的 Temp 布局不可用。应统一 fixture 根路径、边界身份核对及预期值的原生规范化，继续保留精确范围的 adb/MAA 替代边界，补可复现的别名覆盖。不能靠重跑 CI 或放宽为任意后缀匹配解决。

### R1-S1 [P2] `unchanged` 快捷路径掩盖仍需核对的事务

位置：`skills/maa-core/scripts/setup.ts:231–233`。

当四个连接字段已相等，`applySetupConnection` 只检查配置 revision 就返回 `unchanged`，完全绕过共享 writer 的锁核对。可用公开函数先执行一次接入，让 MAA 的替身 `start()` 不建立 ready 状态，得到真实 writer 的 `unknown` 并保留锁；重新 discover 后再 apply，候选实际返回 `{"status":"unchanged","reason":"connection-already-configured"}`。MAA 仍关闭、原未知事务仍未核对。另一个探针在正常接入后创建活跃锁，也返回相同的 `unchanged`，而非 busy。

这违反规格「关闭确认、锁、维护窗口和未知结果规则不变」与 setup 第 5 步「遗留锁交 maa-doctor 核对」；第 6 步及 CLI 把 `unchanged` 当成功，用户会得不到仍需 doctor 处理的结果。无需重写相同字段，但返回成功之前仍须通过共享锁/事务核对，活跃与遗留锁应分别保留 busy / unknown 等待核状态。已有无锁的正常重复接入仍应无写入。

独立复现：`.tmp/r1-probes.test.ts` 的 `already configured connections must still expose active transaction locks` 和 `retry after a failed restart must preserve unknown status until doctor reconciliation`。两条预期拒绝成功的断言均失败于上述实际结果。

### R1-S2 [P2] 连接恢复白名单被同时开放给普通公共写入请求

位置：`skills/maa-core/scripts/maa-config.ts:75–80`。

新分支对任意 `Configurations[profile].Gui.ConnectSettings` 开放四字段，没有要求目标等于 `Current`，也没有区分 setup 本次接入与 doctor 的反向恢复。公开 `executeConfigWrite` 接收普通 `approved-report` 请求、目标为非 Current 的配置序号 1、Address 为合成远端 `192.0.2.1:5555`，不经过 setup 选择/连接复测就返回 `complete`，实际写入该非当前配置。这不是绕过文件系统或调用私有函数：是既有公开 writer 通道的新可达行为，CLI 也调用同一导出函数。

规格 07 明确仅开放「当前配置已有的」四个连接字段，正常接入选择已测试的本机候选；放宽原值是为了 doctor 恢复，不是普通写入请求的额外能力。应把正常连接写入限定到 setup 的本次选择和当前配置，并把恢复旧空值/相对路径/开关的放宽留在已核对的 recovery 路径。不能只依赖 setup 包装函数，因为公共 writer 的普通入口现在也接受这些字段。

独立复现：`.tmp/r1-probes.test.ts` 的 `writer must reject a normal connection request targeting a non-current profile`。实际 `status: complete`、`changedKeys: ["Configurations.<profile>.Gui.ConnectSettings.Address"]`；期望拒绝、文件不变。

### R1-S3 [P2] 损坏设置会中断全部检查且丢失可执行修法

位置：`skills/maa-core/scripts/setup.ts:56`；CLI 映射位置 `273–275`。

把临时设置文件内容改为损坏 JSON 后，运行真实 `node skills/maa-core/scripts/setup.ts check --json`。实际退出 2，仅输出 `{"status":"unexpected-failure","reason":"setup-check-required"}`；没有 settings 检查、原因或修法，连仍可检查的 Windows / Node 也没有返回。原因是已专门识别的 settings 读取失败被立即抛出，CLI 又将 `settings-check-required` 合并为泛化意外失败。

工单 07 要求每次现场检查设置文件，规格「检查与修法」要求每条结果有状态、原因、修法与执行者。损坏设置是这项环境检查的正常错误分支，不应让用户只得到“setup 需要检查”的循环指示。应保留原文件、输出明确的设置损坏/不可读检查和下一步修法（并将未知的私有目录等项保持待核），而不是猜默认值或覆盖设置。

独立复现：`.tmp/r1-probes.test.ts` 的 `corrupt settings must return a diagnostic settings error with repair, keeping original bytes`。原字节确实保留，失败的是检查结果和退出码；没有发生数据破坏。
