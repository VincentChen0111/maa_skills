## 第八轮：Windows CI 发现的解压问题

2026-11-14，PR #70 的 Windows CI 两次在同一个测试失败：MAA 解压得到 failed。原因是 `tar.exe` 按进程的 ANSI 代码页转换条目名，代码页不是中文时，会跳过真实 MAA 包里的 `DependencySetup_依赖库安装.bat`。构建者实测：把 `tar.exe` 的代码页强制设为 1252 或 932 时会跳过中文名，65001 时全部能解。结论：英文、日文系统的用户解不出 MAA 包。

修复 `009d6ab`：
- 改用 Windows PowerShell 5.1 的 .NET `ZipArchive`，路径只经环境变量传入；
- 写入前检查全部条目名，有一条不合格就整包拒绝；
- 不覆盖已有文件，遇到重解析点即停；
- 超过 260 字符的路径也能写。

修复后 Windows CI 通过。

结论：有条件通过，两条 P3。审查员核对后认为以下各点正确：没有注入；56 种构造的条目名都写不到目标外；受约束语言模式下失败关闭。

| 意见 | 处置 | 理由 |
| --- | --- | --- |
| P3：目标路径某一级以空格或点结尾（`MAA `、`MAA.`、`games.MAA`）时，Node 检查并新建的是一个文件夹，脚本 `GetFullPath` 后写进的是另一个（用户已有的 `MAA`），绕过「目标必须为空」 | 接受 | 端到端离线复现；旧的 tar 也是如此，但会往用户没选的文件夹里写文件 |
| P3：`foreach` 读 `$zip.Entries` 时吞掉异常，条目表读不出时退出 0、什么都没解 | 接受 | 离线复现；产品层仍判失败，但解压边界的约定不成立 |

修复 `bff656e`：
- 新增唯一判定 `plainTargetPath`：路径的任何一级以点或空格结尾、含非法字符、是设备名或带路径前缀的，都拒绝为 `target-path-invalid`；
- 脚本比较 `GetFullPath` 的结果与传入的目标，不同就退出 3；
- 条目表改用方法调用读取，计划为空时退出 1。
