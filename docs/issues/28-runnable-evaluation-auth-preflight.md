## 要交付的行为

维护者在本机用一条跟踪在仓库里的命令，就能对任一产品场景或一组场景做真模型评测。开跑之前，不调用模型的预检先证明评测环境是通的，认证预检再证明登录可用；任何一道不通过就停下，不逐场景白跑。每次运行的记录能分清失败原因。评测默认用维护者的套餐登录，登录状态放在专用的登录目录里，只由维护者自己登录，见「决定」。

## 验收条件

- [ ] 跟踪的可复现入口：一条命令按场景名或场景组运行 `eval/` 下任一产品场景（`.ts` 导出），自动装入待测 skill 和它需要的 companion（至少 `maa-core`），不需要另写调用代码。入口跟踪在仓库里并有测试；内置三个演示场景和 `.json` 自定义场景的现有用法不变。
- [ ] 批量和比较：入口能对一个宿主、一个固定模型跑一组场景，把每次的 `run.json` 汇总成一份批次清单；前后比较由跟踪的命令调用 `compareRuns` 完成，输出每个场景的结论和需要单独重跑三次的场景。汇总和比较只读已保存的记录，不改写旧记录。
- [ ] 不调用模型的环境预检，一条命令证明下面各项是通的：临时 home 和工作区建得起来；待测 skill 和 companion 装进了两个宿主目录；Node 观察器记录到一次真实的脚本调用；带 `maaProcess` 的场景里，MAA 进程替身和 daily 观察器可用；带 `networkFixtures` 的场景里，网络替身生效，未列出的请求被拒绝；文件差异和事件被采集到。然后用一个不调用模型的宿主替身，把 `runScenario` 从启动到落盘完整走一遍并评为通过：替身按固定脚本执行场景声明的命令，输出对应宿主格式的记录。预检进离线入口和 CI。它的记录带明确的替身标记，不算模型基线，不能进入 `compareRuns` 的比较，文档里也不写成宿主成功。
- [ ] 认证预检：批量运行之前，对每个要用的宿主探测一次，默认探测套餐登录。先不调用模型：核对即将交给子进程的环境，再用宿主自己的登录状态命令确认专用登录目录里有登录，而且生效的是套餐登录而不是 API key（候选命令 `claude auth status`、`codex login status`，输出格式核实后采用）。然后发一次不给模型任何工具的最小请求。探测失败就停下整批，不再逐场景尝试，并报告属于哪一类：宿主未安装或无法启动、没有登录、登录过期、环境里有 API key、套餐用量上限、网络不通、其他。探测结果写进批次清单，不输出凭据值，也不输出登录目录的路径。显式选了 API key 认证时（决定 9）探测的是 API key，「没有登录」「登录过期」换成「没有配置 API key」「API key 被拒绝」，「环境里有 API key」不适用。CI 里不运行，沿用 CI 禁止启动真实模型的现有约定。
- [ ] 专用登录目录（决定 1）：运行器把每个宿主的配置目录变量（Claude 的 `CLAUDE_CONFIG_DIR`、Codex 的 `CODEX_HOME`）指向该宿主的专用登录目录。两个目录在仓库之外，也在每个场景的临时 home 和工作区之外，不和设置文件指向的私有目录混放；位置落在仓库、临时 home、工作区或私有目录之内时，运行器在启动宿主之前拒绝。这里的私有目录是维护者真实的那一个，不是场景工作区里的那一个（后者已经算在工作区里）。运行器按产品自己的规则只读地定位它：调用 `skills/maa-core/scripts/preferences.ts` 的 `settingsHome` 和 `readSettings`，也就是按 `MAA_SKILLS_HOME` 或默认位置找到设置文件，取其中的私有目录；不另写一份规则。它只拿设置文件所在目录和私有目录这两个路径来比较，不读取私有目录里的任何内容，也不把这两个路径写进记录。这一步读的是产品自己的设置文件里的一个路径值，不是登录文件，和「运行器不复制、不读取维护者日常使用的登录文件」不冲突。每次运行结束后的清理只删临时 home 和工作区，不删、不清空登录目录。运行器和维护者不往登录目录里放登录以外的东西；宿主自己写进去的条目，在第一次真实运行之后按名字（不含内容）列进 `docs/evaluation.md`，核实后采用。位置怎样指定写进 `docs/evaluation.md`，文档和记录里不出现维护者机器上的实际路径。
- [ ] 只由用户登录（决定 2）：运行器、预检和文档给出的步骤里都没有由 agent 输入凭据的一步；目录里没有登录时，预检报告「没有登录」并写明由维护者自己在该目录登录，然后停下。运行器不复制、不读取维护者日常使用的登录文件，`scripts/eval-run.ts` 里「Never copy the caller's auth files」这条约定保留，并有测试断言日常的宿主目录没有被读取或复制。
- [ ] Claude 一侧不带 `--bare`，隔离不变弱（决定 3）：下面每一项都有一个显式开关，或者有记录在案的理由说明专用登录目录已经保证了它：用户级和项目级的记忆文件、自动记忆、hook、插件、宿主自带的 skill、自定义命令、子代理、MCP 服务器、会话持久化、内置工具集。被测模型拿到的工具不超出场景声明的范围：场景没有声明的内置工具不提供给模型。这一条不能只靠 `--allowedTools`，文档写明没有列进去的工具只要不需要批准就照样能运行（候选开关 `--tools`，核实后采用）。待测 skill 和 companion 仍由运行器显式装入工作区。用到的开关逐个对照固定 CLI 版本的文档，并用一次真实运行核实，把宿主实际加载了什么、给了模型哪些工具写进 `docs/evaluation.md`；真实运行出现清单之外的加载项或工具时，这次运行记为 `unverified`，不当作基线。每次升级宿主 CLI 后重新核实一遍，包括 `-p` 是否仍然读取已保存的登录；读不了时 Claude 一侧记为未验证，交回维护者决定。
- [ ] 套餐登录的运行里没有 API key（决定 4）：认证方式由命令行显式指定，不由环境里有没有 `MAA_EVAL_*` 推断。选套餐登录时，子进程环境里没有 `ANTHROPIC_API_KEY`、`ANTHROPIC_AUTH_TOKEN`（Claude）和 `CODEX_API_KEY`、`OPENAI_API_KEY`（Codex），即使设置了 `MAA_EVAL_*` 也不转发；认证预检发现其中任何一个会进入子进程，或者宿主的登录状态显示生效的是 API key，就停下整批。
- [ ] 同一宿主串行（决定 5）：同一个宿主的场景一个接一个地跑，同一时刻只有一个进程在用它的登录目录；批量入口不提供对同一宿主并行的选项。运行器不备份登录文件，也不在批次之间用旧副本覆盖它。
- [ ] 登录目录不外泄（决定 6）：登录目录的路径和其中文件的内容不出现在 `run.json`、`invocation.json`、批次清单、归一化证据和保存下来的原始输出里；路径在落盘之前换成固定的占位符，并纳入「输出里没有凭据」这条评分规则的核对范围。运行器不读取登录文件的内容。逐个宿主核实：被测模型用宿主的文件工具，以及用它被允许执行的命令，都读不到登录目录。哪个宿主做不到，就不在这个宿主上用套餐登录运行：在本票和 `docs/evaluation-verification.md` 里写明做不到的原因，这个宿主的模型验收保持未验证，交回维护者决定。先后顺序：在每个宿主上，这项读保护检查通过之前，不用套餐登录运行任何模型可以用工具的场景，首批试运行也不例外；在这之前，这个宿主上用套餐登录只允许跑认证预检那一次不带工具的最小请求。检查在每一批里排在认证预检之后、第一个带工具的场景之前，没有通过就停下这个宿主的整批。检查不碰真实的登录文件：运行器在登录目录里放一个合成的哨兵文件，提示词要求模型用文件工具读一次，再用一条被允许的命令读一次；两条路都读不到，而且哨兵的值没有出现在输出里，才算通过。检查结果按宿主记进这一批的清单，第一次的结果另记进 `docs/evaluation-verification.md`。
- [ ] 套餐用量上限与续跑（决定 7）：宿主报告套餐用量用尽时，这次运行记为单独的 `unverified` 原因，整批立刻中止，剩下的场景不再启动，也不记成场景失败。批次清单记下已经完成的场景；续跑的命令只跑还没有完成记录的场景。续跑时宿主 CLI 版本、模型、载荷和运行器的指纹必须和原批次一致，不一致就拒绝续跑，另开一批。宿主怎样报告用量用尽，核实后采用；认不出来的仍按原有类别记录。
- [ ] 模型和用量进记录（决定 8）：模型用各家当前名单里的完整 id，不用会漂移的别名。验证记录里 Codex 一侧至今用的 `gpt-6` 不在 2026-11-13 的官方名单里，实现时换成名单里的一个 id 并记下选的是哪个；Claude 一侧记录的 id 也在实现时对照名单。每次运行的记录里有宿主输出中报告的实际模型 id 和 token 用量；宿主没有报告时记为未知，不拿请求的 id 顶替。字段名核实后采用。
- [ ] 首批是小规模试运行：第一批真实运行只跑一个 skill 的场景，两个宿主各一次。把每次运行的 token 用量和耗时写进 `docs/evaluation-verification.md`，据此估出完整批次的用量之后，再开始完整批次。试运行排在该宿主的读保护检查（决定 6）通过之后，没有通过的宿主不做试运行。试运行的记录按普通记录保存，不单独当作基线。
- [ ] 失败原因进记录：`run.json` 带上运行器给出的原因。超时、认证失败、套餐用量上限、宿主未安装、宿主非零退出、记录不完整各是单独的类别，不再合并成 `host-execution-error` 或 `host-failed`。这些类别仍然都评为 `unverified`，评分语义不变。
- [ ] 超时值有依据：默认超时由至少一次真实完成的运行定出。记下那次运行的场景、宿主和耗时，默认值取在它之上留有余量的值，写进 `docs/evaluation.md`，并作为默认值登记到规格两张来源表。有这样一次真实运行之前不改默认值，只把超时单独归类。
- [ ] 补齐 26 要求的场景，两个宿主共用，每个场景都有评分策略、预期调用和预期的文件差异，需要 adb 或 MAA 进程的用边界替身：doctor 正向恢复（遗留事务可以证明时，用户点名批准后调用 repair 并恢复）；setup 正向连接写入（用户确认后经专用入口写入连接设置并读回）；setup 多候选选择（有多个候选时先请用户选，不替用户选）；指定关卡批准后的准备（用户批准报告里的主作业和备选后调用 prepare，配置读回）；跨 skill 交接（覆盖 setup→account→用户批准→daily 这条链，以及 help 和 doctor 各自把用户引到正确入口，两者都要有）。跨 skill 场景需要运行器一次装入多个操作类 skill。场景名在交付时写进 26 的对应验收条目。
- [ ] 文档一致性测试：一个离线测试扫描 `skills/` 下每个 `SKILL.md` 和 `references/*.md`，提取其中每条脚本命令和示例 JSON，断言脚本文件存在，动作名是该脚本命令行接受的动作，示例 JSON 能解析，并且顶层键是该动作接受的键。不一致时测试失败，指出文件和行。不调用模型，进离线入口和 CI。
- [ ] 核实 Claude 的允许列表：用真实的 Claude Code CLI 核实，skill 规定的「标准输入传 JSON」命令的实际写法（管道、重定向或 here-string），在场景声明的 `Bash(node *xxx.ts *)` 模式和关闭权限提示的设置下是否被放行。结果写进 `docs/evaluation.md`。不放行时，改场景的命令模式或 skill 里规定的调用写法，使两者一致，并由文档一致性测试固定下来。Codex 一侧核实同样的命令在评测的沙箱设置下能执行。没能核实的宿主记为未验证。
- [ ] 指纹和旧记录：运行器源码计入场景指纹（`scripts/eval-run.ts` 第 71、77 行），所以本票交付后的记录和旧记录不可比。旧记录原样保留，不改写，不当作新规则下的结果。Claude 一侧带 `--bare` 和不带 `--bare` 的记录同样不可比：两种认证方式用同一套不带 `--bare` 的参数，这个差别只出现在新旧运行器之间，已经由运行器指纹分开。认证方式（套餐登录或 API key，只记类别）写进批次清单。

## 决定

维护者 2026-11-13：「我可以用claude/gpt plan subscription吗？api太贵了」。协调者答复：两家的官方文档都支持这种用法，依据见下面「官方文档写了什么」。维护者随后确认把这项决定写进本票。所以：**行为评测默认用维护者的 Claude 和 ChatGPT 套餐登录认证，不用 API key。**

引号里的那一句是维护者原话。下面编号的各条是协调者 2026-11-13 定的设计默认值，不是维护者原话；规格「规则来源」和「默认值及其来源」里有对应的行，维护者说一声就可以改。标着「核实后采用」的内容还没有在固定的 CLI 版本上核实：实现时先核实，结果写进 `docs/evaluation.md`，核实不了的如实记为未验证。

1. 登录状态放在两个专用、持久的登录目录里，两个宿主各一个：Claude 的配置目录（`CLAUDE_CONFIG_DIR`）和 Codex 的 `CODEX_HOME`。目录在用户主目录下的专用位置，在仓库之外，也在每个场景的临时 home 和工作区之外；不和设置文件指向的私有目录混放。运行器和维护者不往目录里放登录以外的东西：没有维护者日常使用的配置、skill、记忆或会话，维护者日常的宿主会话也不用这两个目录。宿主自己可能往配置目录里写缓存或状态，写了什么在第一次真实运行时列出来，核实后采用。每次运行的清理不删它们。理由：要复用套餐登录，又不能把维护者日常的配置、skill 和记忆带进评测；私有目录里的文件由各 skill 读写，登录状态不属于任何 skill；Codex 的文档写明命令行和编辑器扩展共用同一份登录缓存，日常会话和评测同用一个目录就做不到第 5 条。
2. 只有用户自己登录：每个目录登录一次，过期之后再登录一次。agent 不输入凭据。运行器不复制、不读取用户日常使用的登录文件，`scripts/eval-run.ts` 现有的约定「Never copy the caller's auth files」保留。理由：规格「安全边界」写明登录只由用户手动完成；复制日常登录文件等于把日常登录交给评测。
3. Claude 一侧的运行去掉 `--bare`，两种认证方式都一样。去掉的理由是外部事实：bare 模式不读取 OAuth 凭据，带着它就用不了套餐登录。隔离改由别的手段保证：专用的配置目录，加上针对下列各项的显式开关——用户级和项目级的记忆文件、自动记忆、hook、插件、宿主自带的 skill、自定义命令、子代理、MCP 服务器、会话持久化、内置工具集。这份清单对应文档里 bare 模式做的事，再加上运行器已有的不保存会话：bare 模式跳过 hook、skill、自定义命令、子代理、已安装插件、MCP 服务器、自动记忆和 CLAUDE.md 的自动发现，并且只给模型 Bash、读文件和改文件三类工具。去掉 `--bare` 之后别的内置工具会回来；文档又写明没有列进 `--allowedTools` 的工具只要不需要批准就照样能运行，所以被测模型拿到的工具要另外限制在场景声明的范围内。待测 skill 和 companion 仍由运行器显式装入工作区。有哪些开关、每个开关管到哪里，核实后采用：对照固定 CLI 版本的文档，并用一次真实运行确认。文档里出现过的候选有参数 `--setting-sources`、`--strict-mcp-config`、`--no-session-persistence`（现在已经在用）、`--safe-mode`、`--tools`、`--disable-slash-commands`，环境变量 `CLAUDE_CODE_DISABLE_AUTO_MEMORY`、`CLAUDE_CODE_DISABLE_CLAUDE_MDS`、`CLAUDE_CODE_DISABLE_BUNDLED_SKILLS`，设置项 `disableAllHooks`、`autoMemoryEnabled`、`disableBundledSkills`；这里只列名字，不当作已核实的事实。两种认证方式用同一套参数的理由：否则同一份运行器源码会产出带和不带 `--bare` 两种记录，指纹分不开。带和不带 `--bare` 的记录不可比；这个差别只在新旧运行器之间，运行器源码计入场景指纹，已经分开。真实运行出现清单之外的加载项或工具时，这次运行记为 `unverified`，不当作基线；理由：多出一项没有列出的加载，隔离就没有得到证明，这样的记录不能当作比较的起点。每次升级宿主 CLI 之后重新核实一遍，包括 `-p` 是否仍然读取已保存的登录，读不了时 Claude 一侧记为未验证，交回维护者决定；理由：文档预告 `--bare` 将成为 `-p` 的默认，而 bare 模式不读取登录，见下面「非交互运行」一条。
4. 用套餐登录的运行，子进程环境里没有该宿主的 API key 变量：Claude 是 `ANTHROPIC_API_KEY`、`ANTHROPIC_AUTH_TOKEN`，Codex 是 `CODEX_API_KEY`、`OPENAI_API_KEY`。认证预检发现其中任何一个就停下整批。理由：环境里有 key 时，运行会不声不响地改走按量计费的 API。Claude 的文档写明 `-p` 下只要有 `ANTHROPIC_API_KEY` 就一定使用。Codex 的文档写明 `CODEX_API_KEY` 可以给单次 `codex exec` 指定 API key，没有写它和已保存的登录并存时谁优先；这一点核实后采用，核实之前按「会覆盖登录」处理。Claude 的文档里排在套餐登录之前的其他凭据来源（云厂商开关、`apiKeyHelper`、`CLAUDE_CODE_OAUTH_TOKEN`、profile 变量）是否也要清掉，实现时对照同一页的顺序逐项确认。
5. 同一个宿主的场景串行运行，共用该宿主的登录目录；登录文件不在批次之间从备份恢复。理由：Codex 的文档写明刷新会把新令牌原地写回登录文件，一份登录文件只给一条串行的任务流用，不在并发任务之间共用，也不要每次运行都拿最初的副本覆盖它。Claude 的文档没有把刷新写到这么细，按同样的做法处理。两个宿主各用各的目录，彼此是否同时运行不作限制。
6. 登录目录和其中的内容不出现在运行记录、日志和保存的产物里，由「输出里没有凭据」的评分规则和公开前的隐私检查覆盖。沙箱和允许列表要让被测模型读不到登录目录：逐个宿主核实后采用，要覆盖宿主的文件工具和模型被允许执行的命令。候选手段是 Claude 的 `Read(...)` 拒绝规则和沙箱的 `denyRead` 设置、Codex 的沙箱设置；读到的 Codex 文档没有写沙箱里的命令能不能读工作区之外的文件。哪个宿主做不到，就在本票里写明并停下，不在这个宿主上用套餐登录运行。理由：登录文件等同于密码，被测模型和它调用的脚本用不着它。先后顺序：在每个宿主上，读保护检查通过之前，不用套餐登录运行任何模型可以用工具的场景，首批试运行也一样；在这之前只允许认证预检那一次不带工具的最小请求。检查用放在登录目录里的合成哨兵文件，不用真实的登录文件：提示词要求模型用文件工具和一条被允许的命令各读一次，两条路都读不到、哨兵的值不出现在输出里才算通过。理由：不这样排，第一次带工具的运行就落在保护还没有核实过的宿主上；现在运行器给 Codex 的沙箱参数是 `workspace-write`，它拦不拦得住工作区之外的读取还没有核实。
7. 撞到套餐用量上限是单独的 `unverified` 原因，并且中止整批；它不是场景失败。批次可以稍后续跑，已经完成的场景不重跑；续跑要求指纹和原批次一致。理由：套餐用量和维护者自己的日常使用共用，用尽之后继续逐场景尝试只会得到一串同样的失败；同一批的记录要能放在一起比较，所以续跑不换 CLI、模型、载荷和运行器。
8. 模型 id 固定为各家当前名单里的 id；实际使用的 id 从宿主自己的输出里读出并记录；每次运行的 token 用量也从宿主输出里记录。字段名核实后采用：候选是 Claude 结果消息里的 `modelUsage` 和用量字段、Codex `--json` 的 `turn.completed` 事件里的 `usage`。第一批真实运行先做小规模试运行。理由：可复现；一批要用掉多少套餐用量，在第一次运行完成之前无从得知。
9. API key 认证保留为可选项，沿用现有的 `MAA_EVAL_*` 转发，但不是默认；要用时在命令行显式指定。每个 CLI 实际读取哪个变量，对照固定的 CLI 版本核实后采用。理由：某个宿主用不了套餐登录时（例如做不到第 6 条），维护者仍有一条不用改代码的路；显式指定是为了不让环境里遗留的变量悄悄改变计费方式。
10. 公开 CI 不变：不启动真实模型，不持有任何凭据（用户故事 63）。专用登录目录只存在于维护者本机。

### 官方文档写了什么

以下是 2026-11-13 读到的内容，按意思转述。文档会变，实现时对照固定的 CLI 版本重读一遍。

Claude Code：

- [认证](https://code.claude.com/docs/en/authentication.md)：多种凭据并存时按一个固定的顺序选用，套餐登录排在最后，`ANTHROPIC_AUTH_TOKEN` 和 `ANTHROPIC_API_KEY` 排在它前面。文档只给了这一个顺序，对 `-p` 只多写了一句：有 `ANTHROPIC_API_KEY` 就一定使用。`claude setup-token` 生成一个长期的 OAuth 令牌，打印在终端里、不保存，经 `CLAUDE_CODE_OAUTH_TOKEN` 使用，需要订阅套餐；bare 模式不读这个变量。每个 `CLAUDE_CONFIG_DIR` 目录有自己的设置、会话历史和登录；Windows 上登录保存在配置目录下的 `.credentials.json`。登录过期且无法刷新时，请求失败，直到重新登录。
- [非交互运行](https://code.claude.com/docs/en/headless.md)：bare 模式从不读取 OAuth 凭据和系统钥匙串；它跳过 hook、skill、自定义命令、子代理、已安装插件、MCP 服务器、自动记忆和 CLAUDE.md 的自动发现，只给模型 Bash、读文件和改文件三类工具。不带 `--bare` 时，`-p` 会像交互会话一样发现并加载 hook、skill、插件、MCP 服务器、自动记忆和 CLAUDE.md，包括工作目录和配置目录里的。没有列进 `--allowedTools` 的工具，只要不需要批准就照样能运行。同一页还写着：`--bare` 是脚本调用的推荐模式，将来会成为 `-p` 的默认。所以每次升级宿主 CLI 之后，要重新核实 `-p` 是否还读取已保存的登录；读不了时 Claude 一侧记为未验证，交回维护者决定。
- [命令行参考](https://code.claude.com/docs/en/cli-reference.md)：`claude setup-token` 的说明是给 CI 和脚本生成长期 OAuth 令牌；`claude auth status` 以 JSON 输出登录状态，其中有当前认证方式的字段。`--bare` 一行同样写着它跳过哪些自动发现、只留 Bash、读文件和改文件三类工具；`--allowedTools` 一行写着，要限制有哪些工具可用，改用 `--tools`。
- [环境变量](https://code.claude.com/docs/en/env-vars.md)：`CLAUDE_CONFIG_DIR` 改变配置目录的位置，设置、会话历史和插件都在这个目录下。
- [设置参考](https://code.claude.com/docs/en/settings-reference.md)：第 3、6 条里列的设置项出自这一页；登录保存的位置以认证页为准。
- [模型配置](https://code.claude.com/docs/en/model-config.md)：别名会随时间指向新的版本，要固定就用完整的模型名；JSON 输出时，实际使用的模型在结果消息的 `modelUsage` 字段里。

本票默认用登录目录，不用 `setup-token` 的令牌：令牌只打印一次，要由用户另找地方保存再放进环境变量，两个宿主就成了两套做法。

Codex CLI：

- [非交互模式](https://learn.chatgpt.com/docs/non-interactive-mode)：`codex exec` 默认复用已保存的命令行登录。`CODEX_API_KEY` 可以给单次运行指定 API key。`--json` 输出的 `turn.completed` 事件带 `usage`，示例里有输入、缓存输入、输出和推理输出四个 token 数。`--ignore-user-config` 让运行不加载 `CODEX_HOME` 下的 `config.toml`；现在的运行器带着这个参数，它会不会影响登录的读取，核实后采用。
- [认证](https://learn.chatgpt.com/docs/auth?surface=cli)：登录缓存在 `auth.json` 或操作系统的凭据库里；选文件存储时，`auth.json` 在 `CODEX_HOME` 下。页面列出了几种存储方式，没有写默认是哪一种，所以「登录就在专用目录的 `auth.json` 里」核实后采用。使用期间令牌会自动刷新。`auth.json` 要当作密码对待。`codex login status` 显示当前生效的认证方式。命令行和编辑器扩展共用同一份登录缓存。
- [在 CI/CD 里维持账号登录](https://learn.chatgpt.com/docs/auth/ci-cd-auth)：刷新和串行的要求见第 5 条，对自动化的说法见下一小节。
- [定价](https://learn.chatgpt.com/docs/pricing)：本地消息和云端对话共用套餐的用量额度，按套餐可能有五小时和每周的限额；用尽之后可以买额外额度，或者改用 API key 按 API 价格计费。这句话没有点名 `codex exec`；非交互模式那一页说，需要 ChatGPT/Codex 的用量限额而不是 API key 用量的用户可以走账号登录。exec 的运行怎样计入、用尽时宿主输出什么，核实后采用。
- [模型](https://learn.chatgpt.com/docs/models?surface=cli)：2026-11-13 的名单里没有不带后缀的 `gpt-6`，带 `gpt-6` 前缀的 id 都有后缀。`docs/daily-verification.md` 记录的 Codex 模型是 `gpt-6`，处理办法见验收「模型和用量进记录」。

### 两家对自动化的说法

- OpenAI：CI/CD 那一页写明，给自动化认证的正确做法是 API key；账号登录这条路只面向可信的私有自动化，并且写着不要用于公开或开源仓库的工作流。本票的评测只在维护者本机运行，不进 CI，登录文件不进仓库；但被评测的是一个公开仓库的内容。这一点如实记在这里。
- Anthropic：文档把 `claude setup-token` 描述为给 CI 和脚本用的长期令牌；读到的这几页没有对本机 `-p` 使用套餐登录另作限制，同时预告 `--bare` 将成为 `-p` 的默认。
- 两家的使用条款本票没有审阅。套餐登录能不能长期用于这类评测，以两家的条款为准，由维护者判断。

## 验证方式

入口、批量清单、失败归类和宿主替身都先在导出函数和命令行接缝写失败测试，使用真实临时目录；宿主替身只替代模型调用这一处网络边界，脚本调用、锁和文件差异都是真实的。环境预检和文档一致性测试进离线入口后，在 Windows 和 Ubuntu 的 CI 上各跑一次。认证预检用边界替身覆盖各类失败。

套餐登录这一部分，下面几项用宿主替身和一个充当登录目录的临时目录离线测试，进离线入口和 CI，不需要真实登录：

- 选套餐登录时，子进程环境里没有四个 API key 变量，设置了 `MAA_EVAL_*` 也不转发；key 会进入子进程时预检停下整批。
- 登录目录落在仓库、临时 home、工作区或私有目录之内时被拒绝，私有目录由一份替身设置文件指定（测试把 `MAA_SKILLS_HOME` 指向临时目录，里面放合成的设置文件）；运行后的清理不动登录目录；日常的宿主目录没有被读取或复制。
- 同一宿主的场景串行启动：替身记下每次的启动和结束时间，彼此没有重叠。
- 替身输出用量上限的记录时整批中止，这次运行是单独的 `unverified` 原因；续跑只跑没有完成的场景，指纹不一致时拒绝。
- 记录、批次清单和保存的输出里没有登录目录的路径。
- 某个宿主的读保护检查没有通过时，批量入口不在它上面用套餐登录启动任何带工具的场景；替身读到哨兵文件或者输出里出现哨兵的值时，检查记为不通过。
- 替身输出里的模型 id 和 token 用量进了记录，缺失时记为未知。

下面几项需要真实宿主和维护者的套餐登录，只在维护者本机做；没有做的如实记为未验证，不写成通过：

- 认证预检的真实探测；
- 不带 `--bare` 时 Claude 实际加载了什么、给了模型哪些工具；
- 两个宿主各自的读保护检查（哨兵文件），排在该宿主任何带工具的套餐登录运行之前；
- 宿主自己往登录目录里写了什么；
- 各项「核实后采用」：字段名、登录状态命令的输出、用量上限的报告方式、每个 CLI 实际读取的变量；
- 首批试运行的用量和耗时；
- 允许列表核实和超时取值。

需要维护者本人做的只有一件事：在两个专用登录目录里各登录一次，过期后重新登录。

## 实现与交付约定

有代码行为的改动先写外部行为测试，使用真实临时目录，只替代 MAA 进程、adb 和网络；skill 改动按同模型、同场景做前后评测，真模型只在本机运行。每个改动包经一个独立审查员审查，最多三轮，记录意见处置和结论；公开前检查所有移植文件及合成样例的隐私，经分支、PR 和 squash 合并。

构建与评测使用临时 home，不改动维护者现有 MAA、已安装 skill 或私有生产环境。专用登录目录是唯一的例外：它在临时 home 之外，是持久的，只由维护者自己登录，见「决定」。沿用本票所列规格决定；新增或修改限制时在规格两张来源表登记来源。
