## 要交付的行为

维护者在本机用一条跟踪在仓库里的命令，就能对任一产品场景或一组场景做真模型评测。开跑之前，不调用模型的预检先证明评测环境是通的，认证预检再证明凭据可用；任何一道不通过就停下，不逐场景白跑。每次运行的记录能分清失败原因。

## 验收条件

- [ ] 跟踪的可复现入口：一条命令按场景名或场景组运行 `eval/` 下任一产品场景（`.ts` 导出），自动装入待测 skill 和它需要的 companion（至少 `maa-core`），不需要另写调用代码。入口跟踪在仓库里并有测试；内置三个演示场景和 `.json` 自定义场景的现有用法不变。
- [ ] 批量和比较：入口能对一个宿主、一个固定模型跑一组场景，把每次的 `run.json` 汇总成一份批次清单；前后比较由跟踪的命令调用 `compareRuns` 完成，输出每个场景的结论和需要单独重跑三次的场景。汇总和比较只读已保存的记录，不改写旧记录。
- [ ] 不调用模型的环境预检，一条命令证明下面各项是通的：临时 home 和工作区建得起来；待测 skill 和 companion 装进了两个宿主目录；Node 观察器记录到一次真实的脚本调用；带 `maaProcess` 的场景里，MAA 进程替身和 daily 观察器可用；带 `networkFixtures` 的场景里，网络替身生效，未列出的请求被拒绝；文件差异和事件被采集到。然后用一个不调用模型的宿主替身，把 `runScenario` 从启动到落盘完整走一遍并评为通过：替身按固定脚本执行场景声明的命令，输出对应宿主格式的记录。预检进离线入口和 CI。它的记录带明确的替身标记，不算模型基线，不能进入 `compareRuns` 的比较，文档里也不写成宿主成功。
- [ ] 认证预检：批量运行之前，对每个要用的宿主探测一次凭据，用当前配置的认证方式发一次最小的请求。探测失败就停下整批，不再逐场景尝试，并报告属于哪一类：宿主未安装或无法启动、没有配置认证、认证被拒绝、网络不通、其他。探测结果写进批次清单，不输出凭据值。它支持当前配置的任一种认证方式，见「待维护者决定」。CI 里不运行，沿用 CI 禁止启动真实模型的现有约定。
- [ ] 失败原因进记录：`run.json` 带上运行器给出的原因。超时、认证失败、宿主未安装、宿主非零退出、记录不完整各是单独的类别，不再合并成 `host-execution-error` 或 `host-failed`。这些类别仍然都评为 `unverified`，评分语义不变。
- [ ] 超时值有依据：默认超时由至少一次真实完成的运行定出。记下那次运行的场景、宿主和耗时，默认值取在它之上留有余量的值，写进 `docs/evaluation.md`，并作为默认值登记到规格两张来源表。有这样一次真实运行之前不改默认值，只把超时单独归类。
- [ ] 补齐 26 要求的场景，两个宿主共用，每个场景都有评分策略、预期调用和预期的文件差异，需要 adb 或 MAA 进程的用边界替身：doctor 正向恢复（遗留事务可以证明时，用户点名批准后调用 repair 并恢复）；setup 正向连接写入（用户确认后经专用入口写入连接设置并读回）；setup 多候选选择（有多个候选时先请用户选，不替用户选）；指定关卡批准后的准备（用户批准报告里的主作业和备选后调用 prepare，配置读回）；跨 skill 交接（至少覆盖 account 的建议条目经用户批准后由 daily 执行，以及 help 或 doctor 把用户引到正确入口）。跨 skill 场景需要运行器一次装入多个操作类 skill。场景名在交付时写进 26 的对应验收条目。
- [ ] 文档一致性测试：一个离线测试扫描 `skills/` 下每个 `SKILL.md` 和 `references/*.md`，提取其中每条脚本命令和示例 JSON，断言脚本文件存在，动作名是该脚本命令行接受的动作，示例 JSON 能解析，并且顶层键是该动作接受的键。不一致时测试失败，指出文件和行。不调用模型，进离线入口和 CI。
- [ ] 核实 Claude 的允许列表：用真实的 Claude Code CLI 核实，skill 规定的「标准输入传 JSON」命令的实际写法（管道、重定向或 here-string），在场景声明的 `Bash(node *xxx.ts *)` 模式和关闭权限提示的设置下是否被放行。结果写进 `docs/evaluation.md`。不放行时，改场景的命令模式或 skill 里规定的调用写法，使两者一致，并由文档一致性测试固定下来。Codex 一侧核实同样的命令在评测的沙箱设置下能执行。没能核实的宿主记为未验证。
- [ ] 指纹和旧记录：运行器源码计入场景指纹（`scripts/eval-run.ts` 第 71、77 行），所以本票交付后的记录和旧记录不可比。旧记录原样保留，不改写，不当作新规则下的结果。
- [ ] 文档：`docs/evaluation.md` 写明新入口、两道预检、失败类别和超时依据；`docs/evaluation-verification.md` 记录实际运行的结果和未验证项。本票不建立任何模型基线，基线仍由 26 验收。

## 待维护者决定

评测怎样登录还没有决定，本票不选默认值：

- 评测专用的 API key，经 `MAA_EVAL_OPENAI_API_KEY`、`MAA_EVAL_ANTHROPIC_API_KEY` 转发。这是现在跟踪的运行器唯一支持的方式。
- 专用的评测登录目录：只给评测用的宿主登录状态，由运行器指向它，不复制维护者日常使用的登录目录。现在的运行器不支持。

除认证预检外，上面的交付物都不依赖选哪一种。认证预检按「当前配置了哪一种，就探测哪一种」实现：探测是一个接口，转发 API key 这一种随本票交付。维护者如果选了登录目录，接入它的改动在那次决定之后登记，预检沿用同一个接口。两种都没有配置时，预检报告「没有配置认证」并停下，不发起模型调用。

## 验证方式

入口、批量清单、失败归类和宿主替身都先在导出函数和命令行接缝写失败测试，使用真实临时目录；宿主替身只替代模型调用这一处网络边界，脚本调用、锁和文件差异都是真实的。环境预检和文档一致性测试进离线入口后，在 Windows 和 Ubuntu 的 CI 上各跑一次。认证预检用边界替身覆盖各类失败。认证预检的真实探测、允许列表核实和超时取值需要真实宿主和可用的认证，只在维护者本机做；没有做的如实记为未验证，不写成通过。

## 依赖理由

03 提供运行器、评分规则和样例自检。[27](27-approved-stone-expiring-medicine.md) 也改评分规则、场景清单和运行器的内置演示；两票改到同一批文件时，后合并的一方变基，并重新确认场景指纹。26 依赖本票：没有可运行的入口和预检，26 的模型验收无法执行。

## 实现与交付约定

有代码行为的改动先写外部行为测试，使用真实临时目录，只替代 MAA 进程、adb 和网络；skill 改动按同模型、同场景做前后评测，真模型只在本机运行。每个改动包经一个独立审查员审查，最多三轮，记录意见处置和结论；公开前检查所有移植文件及合成样例的隐私，经分支、PR 和 squash 合并。

构建与评测使用临时 home，不改动维护者现有 MAA、已安装 skill 或私有生产环境。沿用本票所列规格决定；新增或修改限制时在规格两张来源表登记来源。
