## 验收条件

- [ ] 建立 setup/doctor 共用的检查与修法接口，以配置解析和写入锁检查贯通；每条结果有正常/提醒/错误状态、原因、修法及由 skill 或用户执行的类别。
- [ ] 默认诊断只读；除最近检查记录外不修改配置或锁。每项修法先获批准，可一次点名多项，不提供笼统「全部修复」。
- [ ] 区分活跃持有者和遗留锁；遗留锁核对当前配置、最新备份和 MAA 运行状态，展示哪些已生效、哪些仍未知，核对完成后才清除。
- [ ] 批准的配置恢复仍调用 05 的写入通道；doctor 不增设旁路，继续遵守进程、定时窗口和禁止设置规则。
- [ ] 结果未知不会触发原操作的自动重放；不能证明恢复完成时保留证据并交接，不宣称已恢复。
- [ ] 提供人类可读及 --json 输出，退出码 0 正常（允许提醒）、1 有错误、2 意外失败；最近检查记录包含时间与脱敏结果。

## 验证方式

构造持有者存活、消失、当前配置与备份一致/不同、MAA 开关及损坏配置场景；断言未批准不执行、批准范围外不执行、结果未知不重放，核对 CLI 退出码和记录。

## 实现与交付约定

有代码行为的改动先写外部行为测试，使用真实临时目录，只替代 MAA 进程、adb 和网络；skill 改动按同模型、同场景做前后评测，真模型只在本机运行。每个改动包经一个独立审查员审查，最多三轮，记录意见处置和结论；公开前检查所有移植文件及合成样例的隐私，经分支、PR 和 squash 合并。

构建与评测使用临时 home，不改动维护者现有 MAA、已安装 skill 或私有生产环境。沿用本票所列规格决定；新增或修改限制时在规格两张来源表登记来源。
