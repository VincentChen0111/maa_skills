用户启动已准备批次后，maa-daily 持续跟踪结构化回调，保存运行记录并明确报告每关终态或需要核对的未知状态。

## 验收条件

- [x] 关联准备批次、关卡和本次运行，持续跟踪至成功、失败、未三星、理智不足、明确超时、环境类失败或结果未知的交接状态。
- [x] 依据连接、任务链和子任务的结构化回调分类，不只靠关键词；进程退出码 0 不覆盖回调中的失败。环境类失败（连接、模拟器或游戏客户端、MAA 进程、识别环境）和作业失败分开，不记为该关失败。
- [x] 及时报告失败、未三星、理智不足和明确超时，运行记录带对应证据；不把沉默或短暂没有新日志自动当作失败。
- [x] 断连、进程中断等环境类失败先查明原因并核对当前状态；状态核对清楚后由模型决定：在原批准范围内重试、换下一份已批准的备选（经 17），或者停下告诉用户，并记录理由。重试不增加理智药或碎石的授权数量，启动方式不变（用户点开始，或 MAA 自己的机制）。2026-11-13 补充：本票跟踪的批次经 MAA 的自动战斗运行。固定版本的自动战斗没有理智药数量，也没有碎石：用不用理智药是一个开关，计数上限固定为 999,999（MaaCore `CopilotTask.cpp` 第 36–40、71、200 行）；这个开关是 MAA 自己窗口里的运行时选择（`src/MaaWpfGui/ViewModels/UI/CopilotViewModel.cs` 第 582、2291 行），写入脚本设不了。所以本项目不为这类批次授予理智药或碎石数量。发现批次用了没有经本项目批准的理智药时，运行记录写明，模型告诉用户，不凭「授权够用」的判断自行重试或换作业。日常队列的数量授权和剩余数量由 [27](27-approved-stone-expiring-medicine.md) 交付。结果仍然未知或证据不全时只核对，不重新启动、重打或换作业。
- [x] 能从回调或用户的说明看出用户正在手动玩（模拟器或官方 PC 客户端）、或者手动登录把 MAA 的会话顶下线时，按环境类失败处理，不记为作业失败；继续之前重新读取状态，不沿用批准时的理智、药剂、源石或关卡进度，读不到的标为未知。
- [x] 复用共享诊断分类并向用户给出下一步；日志摘要、运行记录和输出不含凭据、账号标识或完整配置。
- [x] 在临时环境中完整演示从用户开始信号到运行结果的跟踪，不点击游戏或操作设备。
- [x] 回调行解析只有一份：把 `skills/maa-core/scripts/training-state.ts` 里解析 MaaCore 日志回调行（`Assistant::append_callback | <消息名> <JSON>`，依据见[专精来源核对](../training-sources.md)）的部分提成 maa-core 的公共模块，运行跟踪和专精核对都调用它，不各写一份；专精现有的测试保持通过。
- [x] 运行开始前记录日志起点：`debug/asst.log` 和 `debug/gui.log` 各记字节偏移、文件大小、文件身份和末尾一段内容的哈希，跟踪时只把起点之后的行算作本次运行。发现文件被轮换或截断时（固定版本里上一轮 Core 日志在 `debug/asst.bak.log`），到轮换后的文件里接着找；接不上的部分记为证据不全，按结果未知处理，不把整份日志当成本次运行。
- [x] 运行记录的结果分两层：执行状态（已完成、失败、未知）和业务结果（每关的成功、失败、未三星、理智不足等）。业务结果在有对应回调证据之前保持「未评估」，不从执行状态推出；运行结束时仍没有证据的记为结果未知。失败类别直接记 MAA 回调里的消息名和 `what` 值，再对应到第 1 条的终态，不另起一套和 MAA 对不上的类别名。固定版本的回调协议里已核对到 `TaskChainError`、`SubTaskError`，以及 `ConnectionInfo` 的 `ConnectFailed`、`Disconnect`、`Reconnecting`、`Reconnected`、`ScreencapFailed`、`TouchModeNotAvailable`。
- [x] 读 `debug/gui.log` 时先查错误标记，再查完成标记；同一段时间里两者都出现时按错误处理，完成标记不覆盖错误。固定版本的中文界面文案里已核对到「任务出错: 」「战斗出错」「未选择作业」「读取文件失败！」和「完成任务: 」。自动战斗启动失败、自动战斗出错在 `gui.log` 里的实际写法，以及「任务失败后 MAA 仍会写完成任务」这一观察，核实后采用。界面文案随语言和版本变化，所以 `gui.log` 只用来划定时间段和补充说明，分类仍以结构化回调为准（第 2 条）。
- [x] 识别 MAA 原生定时接管了运行：跟踪期间 MAA 的定时启动了别的任务或切换了配置时，本次运行记为被接管，之后的回调不算进本批次；结果按未知处理，先核对当前状态，不重新启动。定时启动在 `gui.log` 和回调里留下的具体痕迹，核实后采用。
- [x] 关卡核对只用回调：把批次里配置的关卡，和掉落回调（`SubTaskExtraInfo` 的 `StageDrops`，其 `details.stage` 带 `stageCode` 和 `stageId`）里实际出现的关卡比较，逐关给出吻合、不符、没有打、未知四种结论，写进运行记录。这项核对不需要图像识别。
- [x] 证据可以引用 MAA 自己已经保存的调试截图，只给路径：`debug/` 下修改时间不早于运行起点的图片文件。固定版本的官方日志分析说明列有 `debug/interface/*.png` 和 `debug/drops/*.png`，`asst.log` 里有对应的保存记录。路径写成相对 MAA 目录的形式。本票不打开这些图片，也不对它们做识别；另加识别要按规格「不在范围」的说明，另开一张写明缺口的工单。
- [x] 2026-11-13 新增：运行记录写明这次运行里 MAA 报告用掉了多少理智药；读不到时记录写「未知」，不写 0。候选来源是 `SubTaskExtraInfo` 里 `what` 为 `UseMedicine` 的 `details.count`（固定版本 MaaCore `MedicineCounterTaskPlugin.cpp` 第 176–201 行），核实后采用；不用 `MedicineConfirm` 的点击次数，因为一次确认可以用掉多瓶。固定版本的自动战斗没有碎石，碎石一项不记。

## 验证方式

回放正常、失败、未三星、无理智、超时、断连、手动会话顶下线及退出 0 但失败的合成结构化事件；验证不会重复执行或误报成功，环境类失败不记为该关失败，添加两宿主行为场景。2026-11-13 补充：再回放日志在运行中途被轮换、错误标记和完成标记同时出现、原生定时接管，以及掉落回调里的关卡和配置不符这四种合成样例；公共回调解析模块有自己的测试，专精的现有测试不改断言。另回放两种样例：回调报告了用药的批次，运行记录带上数量；回调读不到时，记录写「未知」。
