## 背景与目标

实施进度：未开始。

建议报告生成排班不等于用户已允许写入。daily 应清楚辨认批准的版本和条目，再安全应用。

## 要交付的行为

用户批准基建报告中的明确排班后，maa-daily 校验并写入 MAA 自定义基建设置，读回核对并记录结果。

## 规格依据

用户故事：27、37。涉及章节：日常操作；MAA 配置写入；五个 skill 和边界。术语使用父规格关联的术语表。

## 验收条件

- [ ] 识别用户批准的排班及条目，核对输入与批准内容一致；未批准条目和后来修改的内容不随带执行。
- [ ] 应用前运行共享排班校验，报告错误和未持有干员警告；不把无效排班写入配置。
- [ ] 写入只调用 05 的统一通道，覆盖锁、关停、备份、定时窗口、最小改动和读回；不改变 MAA 不支持切换的生产线。
- [ ] daily 只维护配置、待执行和运行记录，不改写 account 的建议报告或快照；未审查标记继续可见，不因执行被改成已审查。
- [ ] 写入失败或结果未知时保留证据并转核对，不自动重放；成功时说明实际改变的项目及可用备份。
- [ ] 不点击游戏、不操作设备，后续基建任务由用户启动或 MAA 自己的机制运行。

## 验证方式

端到端演示报告→用户批准→校验→安全写入→读回；覆盖未批准、报告版本变更、排班无效、写入中断和未知结果，检查无关配置保持。

## 依赖理由

22 提供可验证的排班和批准条目；05 提供唯一配置写入通道。

## 实现与交付约定

有代码行为的改动先写外部行为测试，使用真实临时目录，只替代 MAA 进程、adb 和网络；skill 改动按同模型、同场景做前后评测，真模型只在本机运行。每个改动包经一个独立审查员审查，最多三轮，记录意见处置和结论；公开前检查所有移植文件及合成样例的隐私，经分支、PR 和 squash 合并。

构建与评测使用临时 home，不改动维护者现有 MAA、已安装 skill 或私有生产环境。沿用本票所列规格决定；新增或修改限制时在规格两张来源表登记来源。
