## 背景与目标

实施进度：未开始。

2026-11-16 新增本票，是设计票：写明从 v0.2.0 起，模型评测的「前」「后」怎样比较，才不会再出现比较不了的配对。维护者在 v0.1.0 发布前看过比较不了的 33 对，原话：「这次没关系，但以后怎么处理好？」v0.1.0 凭 Codex 的结果发布，是维护者 2026-11-15 的决定，原话「可以只codex发布」。下文的具体写法是设计默认值，不是维护者原话；维护者确认之前，本票的 triage 状态是 `needs-triage`。

### v0.1.0 发生了什么

[26 的发布验证记录](../release-verification.md)「当前评分器下「前」载荷能不能通过」一节和它的「未验证的比较」表记了经过，要点如下。

- 发布把最终候选和 11 个历史载荷比较：`ddd0ca8`、`1d7fec0`、`370ed68`、`6c582e7`、`ac03ba8`、`788ac13`、`3ff4555`、`fc633d6`、`ac89050`、`6f95f27`、`f1ec4ed`。两侧都在同一个冻结的框架里，用发布时的评分器评分。
- 每个宿主有 33 对比较不了：
  - 发布记录把其中 32 对记为评分契约晚于「前」载荷：不论模型怎样做，「前」都失败。按现在的框架，其中 `daily-close-failure`、`daily-restart-failure` 在 `ddd0ca8` 上的两对，26 H4 第 1 轮起也装 maa-doctor 同伴，入口就以 `payload-skill-missing` 拒绝（发布记录「前后载荷」表 `ddd0ca8` 那一行）。所以只因契约的是 30 对；
  - 另 1 对是 `daily-unknown` 在 `ddd0ca8` 上：场景要 maa-doctor 同伴，而这个载荷早于 06，入口以 `payload-skill-missing` 拒绝。入口拒绝的合计 3 对。
- 另有 3 对有条件未验证：`daily-unknown` 在 `788ac13`、`3ff4555`、`fc633d6` 上，「前」交给 doctor 核对时，只因为旧格式的 doctor 记录才挂 `authorization`。
- 三种契约：
  - 30 的预览与差异指纹；
  - 25 的待执行记录 `versions`；
  - 10、25、08 改过的 doctor 最近检查记录（`checks`、`recovery`、`version`、`skills` 四个键）。
- 为了排除这些配对，发布时先在离线环境里逐个核对，看「前」载荷在当前评分器下能不能通过；逐对写进记录，交维护者决定。

### 根因

1. **前后比较推迟到了发布。**05、06、07、13、14、15、24 都是单票决定：当时隔离认证不可用，把模型前后比较移交 26（规格「发布与维护流程」和「默认值及其来源」里这几票的交付决定）。28 之后评测才能真正运行。所以发布时只能回到 11 个历史提交，重建各自的「前」。
2. **评分契约在这段时间里变了。**评分器要求的记录或动作（25、30、10/25/08），比部分「前」载荷晚。
3. **契约检查和行为检查耦合在一起。**行为检查是不重放、先批准、语言、拒绝这类判断，契约检查判断记录格式。
   - `scripts/eval-daily.ts` 的 `assessDailyTransaction` 和 `scripts/eval-transaction.ts` 的 `assessWriterTransaction` 是全有或全无的解析：
     - 30 的 `preview` 与 `diffFingerprint`、25 的 `versions`、待执行记录和锁的逐字节格式，任何一处不符就返回 `valid: false`；
     - 返回 `valid: false` 时，这次写入的授权和锁事件都不给；
     - 结果是 `scripts/evaluation.ts` `grade()` 里的 `authorization`、`write-lock`、`expected-behavior` 三项一起挂，行为也就比不了。
   - doctor 记录的契约不在这两个函数里，在场景的字面授权里：`eval/maa-doctor/scenarios.ts` 的 `latestRecordGrants`。旧格式记录的键在通用的 `authorization` 里挂。

### 比较不了，丢的是什么

`compareRuns` 里，「后」不通过一律算回归。这一判定在内部函数 `compareScenario` 里：「前」通过而「后」不通过，要先重跑三次再定；两边都不通过，直接记回归。所以这 33 对不会漏掉「后」的失败。丢的是「前」这一侧：

- 工单要求的「前后不降」拿不出证据，只能交维护者豁免；
- 「后」不通过时，没有「前」通过作参照，也就没有三次重跑这条路；
- 为了排除它们，要对每个「前」载荷做离线核对，工作量和发布的其他准备相当。

### 目标

从 v0.2.0 起：

- 每一对前后比较，在行为项上都能比；
- 改了评分契约的那一项，只在「后」侧核对，不让整对比较不了；
- 发布只和上一个发布标签比较，不再回溯各票的历史载荷。

## 对提议方向的评估

协调者转来三条方向。下面逐条给结论；具体规则见下一节。

1. **逐 PR 前后比较。采用。**每个改 agent 可见行为的 PR，在合并前做自己的前后比较：「前」是 PR 的合并基点（main 上的提交），「后」是 PR 头，两侧在同一个冻结的框架提交上跑；发布只和上一个标签比较。
   - 这本来就是 [AGENTS.md](../../AGENTS.md) 的规则（「改 skill 前后固定模型与场景评测，分数不得下降」）。v0.1.0 前各票推迟，原因是当时认证不可用；28 之后可以按规则做了。
   - 「前」是合并基点的 main，已经满足本 PR 之前的全部契约。所以「前」可能早于的契约，只剩本 PR 自己改的那几项。
   - 补充三点：只跑受影响的场景；可以复用上一个 PR 的「后」批次作「前」；合并时用不调用模型的命令核对结果仍然有效。
2. **评分项打 `behavior` / `contract` 标签。采用，但有一处必须补上。**
   - 只给现在的 8 项（`authorization`、`write-lock`、`allowed-keys`、`forbidden-settings`、`secret-output`、`download-confirmation`、`report-review`、`expected-behavior`）打标签不够：契约检查就在其中三项里面，打了标签也会连坐。要把契约部分拆成单独的契约项，行为项不再依赖契约解析的结果（见「一」）。
   - 「只在 PR 有意改契约时才只比行为项」，改成机器可判断的规则：契约项按版本比较，版本两边相同就照常比较，不同才从「前」侧拿掉。
   - 单靠这一条，再加上「发布只和上一个标签比」，就已经消除了比较不了的配对。第 1 条带来的是更早发现、并能定位到哪个 PR，代价是 Codex 用量（见「七」）。
3. **改契约的 PR 在工单里声明，当时重建受影响场景的基线。采用。**
   - 声明要能被机器核对：PR 在契约版本表里给这个契约升版本，和产品改动在同一个 PR 里。比较工具据此算出哪些契约变了。
   - 「重建基线」不用另外跑：这个 PR 的「后」侧运行，就是新契约版本的第一批记录。每个 PR 都会重跑自己的「前」，不需要长期维护的基线。

## 要交付的行为

### 一、评分项分成行为项和契约项

- **行为项**：规格要求的、与产品版本无关的判断。例如：
  - 用户的状态（MAA 配置、凭据、偏好、MAA 文件）只按授权改动，只碰允许的键，不开禁止的设置；
  - 输出里没有秘密；下载前问过用户；报告经过独立审查；批准记录与场景声明一致；
  - 跑了哪些产品动作、各几次：不重放、不调用被禁止的 repair、只有一次计入的写入、被拒后不自称已经关闭 MAA；
  - 最后的状态对不对；回复里的语言、拒绝和提问。
- **契约项**：产品某个版本起才定下的格式。例如：
  - 产品自己的记录（待执行记录、运行记录、备份命名、锁文件内容、doctor 最近检查记录、setup 环境记录、生成文件的固定字段）的字段和字节；
  - CLI 协议里某张票引入的步骤和字段，例如 30 的 `preview` 和 `diffFingerprint`、25 的 `versions`。
- **分类规则**：
  - 判断一项是不是行为项，要问：这一项换到任何一个有这个功能的载荷上，意思都不变吗？变就是契约项。
  - 行为项可以读产品 CLI 请求里的字段，但只能读写入器第一版（05）起没有变过的字段，例如 `closedConfirmed`。以后要改这样的字段，按契约变更处理，把读它的检查拆开。
  - 场景期望的产品 CLI 动作也要分类。出现在 `expectedInvocations` 里的每个（文件、动作），要么登记在 `eval/contracts.ts` 的某个契约下，要么列在注册表的稳定动作清单里，并注明从哪张票起就有。新加的动作在 main 上一定还没有，所以只能登记为契约；30 的 `preview` 就是这一类。
- **契约注册表**，分两个文件：
  - `eval/contracts.ts` 列出每个契约的 id、它管的产品记录路径（或路径模式）和 CLI 动作或字段、引入它的工单。它在评分器的导入闭包里，改它会改变场景指纹。
  - `eval/contract-versions.json` 只记每个契约的版本号和改过它的工单。评分器不导入它，所以只升版本号不改变运行器指纹和场景指纹。
  - 本票交付时，现有的每个契约都记版本 1。
- **不连坐**：
  - 行为项只读与版本无关的证据：`transcript`；观察器的调用事件（文件、动作、退出码、pid）；daily 观察器记的动作序列和进程动作；`changes` 里用户状态文件的差异；上面说的稳定请求字段。
  - 契约解析失败，只让对应的契约项不通过，不撤销行为项需要的授权和事件。
  - 产品记录路径上的改动，在行为层面只核对一件事：这个运行调用过注册表里写这个路径的产品命令。记录内容对不对，由契约项判。既调用了命令、又手改了记录的运行，由「后」侧的契约项拦下：契约项照字面授权逐字节核对，手改的内容对不上。
- **评分结果的形状**：
  - `grade()` 返回 `items[]`，每项有 `id`、`tag`（`behavior` 或 `contract`）、`contract`（契约项才有）和 `status`（`pass`、`fail`，契约项还可以是 `not-applicable`）。
  - 现在的 8 项保留名字，作为行为项，去掉其中的契约部分。契约项以 `contract:<id>` 命名；场景用到的契约（例如有提醒事务、doctor 记录授权）才适用。
  - `status`、`score`、`total`、`failed` 照旧给出：`status` 看全部适用项，`failed` 列出不通过的项名。
- **总判定不变**：一份运行全部通过（行为项加适用的契约项），当且仅当按现在的评分器通过。拆分只改变失败记在哪一项，不放宽，也不收紧。

现在的检查按这条规则的初步分类如下，实现时逐个核对：

| 现在的检查 | 位置 | 分类 |
| --- | --- | --- |

### 二、比较规则

只有 `scripts/evaluation.ts` 一处负责可比性，这一点不变。

- **契约变更集**：
  - 一个契约在「前」「后」两侧的版本不同，就进变更集。由 `scripts/evaluation.ts` 里的一个纯函数算出，输入是两侧的版本表。
  - 「后」的版本表取正在评分的框架检出里的 `eval/contract-versions.json`。「前」的取「前」载荷那个提交里的同一个文件，提交里没有这个文件时，全部算版本 0。
  - 「前」是 `checkout` 来源时，取检出自己的版本表。
  - 读不到「前」的版本表时（例如浅克隆里没有那个提交），整对比较不了，原因 `contract-versions-unreadable:before`。
- **`compareRuns` 逐场景的判定**：
  - 可比项是行为项，加上版本两边相同的契约项。变更集里的契约项不进「前」侧的判定。
  - 「前」的判定只看可比项；「后」的判定看全部适用项，包括变更集里的契约项。
  - 其余规则不变：「前」通过、「后」不通过，重跑三次（重跑看全部适用项），三次全过记 `unstable`，否则记回归；两边都不通过记回归；「后」通过记通过。比较分数时只数可比项。
  - 记录没有 `items`（本票之前的记录）时比较不了，原因 `grade-items-missing:<边>`。
  - 同一场景两边的项不同时比较不了，原因 `grade-items-differ:<场景>`，取代现在的 `grade-total-differs`。
  - 现有的其他原因和优先次序不变。
- **`batchIncomparability`**：规则不变，两批仍然只允许载荷不同。契约版本不进批次条件：它由载荷提交和框架检出决定，在比较时算。
- **`scripts/eval-batch.ts` 的 `compare`**：
  - 输出新增 `contracts: { before, after, changed }`；`changed` 里每项有 id、两侧版本，以及「后」侧版本表记的工单。
  - `scenarios[]` 每条新增两个字段：
    - `excludedContracts`：这个场景适用、在变更集里的契约项；
    - `contractBeforeFailures`：版本两边相同、只在「前」侧不通过的契约项；
    - `behaviorBeforeFailures`：只在「前」侧不通过、「后」通过的行为项。
  - `passToFail` 按可比项计算。
  - 退出码仍然来自同一个判定，帮助文字同步更新。

### 三、逐 PR 的前后比较

- **哪些 PR 要跑**：合并基点和 PR 头的评测载荷摘要不同的 PR，都要跑。
  - **评测载荷摘要**：载荷（`skills/`、`.claude-plugin/`）按豁免表规范化之后的内容摘要。由一个导出函数算出；批次清单的 `payload` 在 `digest` 之外另记 `evaluatedDigest`，`payload` 命令也输出它。
  - **豁免表**：机器可读，放在 `eval/payload-exemptions.ts`，[行为评测](../evaluation.md) 里列同一张表。初始三行：
    - 每个 skill 目录里的 `LICENSE`：整份不计；
    - `skills/maa-core/package.json`：`version` 的值换成同一个占位后再计，别的字段照常计；
    - `skills/maa-core/references/verified-versions.json`：`recordVersion`、`sourceVerified`、`deviceVerified` 三个键保留，值换成同一个占位后再计。25 的每日 Action 只改这三项；`schemaVersion` 和键的集合照常计，格式变了就不算豁免。
  - **豁免的理由**：这些改动不改变 agent 读到的指令。场景里的核实记录版本由夹具在运行时从装入的记录读出（`{{maa-record-version}}`），合成的 MAA 读不到版本，核实行不影响任何场景的期望。发布那次比较跑全部场景，豁免的改动最晚在那里被比较到。
  - 豁免表不进运行器指纹：它不影响任何一次运行的评分。改了豁免表，之前清单里记的评测载荷摘要就和新算的对不上，按下面的判定重跑。
- **框架 PR**：只改评分器、场景或运行器、不改载荷的 PR，不跑模型。离线入口里的场景测试（宿主替身驱动）证明，当前 main 载荷的正确做法在新评分下通过，错误做法不通过。真实模型在新评分下的表现，由下一个改载荷的 PR 的「前」侧，或下一次发布看到。
- **跑哪些场景**：新增一条不调用模型的命令，在两个载荷上列出三类，每个场景附理由：
  - **比较**：装入的 skill 文件两侧不同，并且「前」载荷能做的场景。用逐场景的载荷指纹判断，文件先按豁免表规范化，只差豁免部分不算不同。两侧场景定义相同，所以载荷指纹不同就等于装入的文件不同。
  - **只跑「后」**：本 PR 新增的场景、「前」载荷做不了的场景，以及装入文件两侧相同但本 PR 改了定义的场景。
  - **不跑**：其余场景。
- **一侧只认一个批次**：一次比较，「前」「后」各只用一个批次（另加重跑批次）。`compareRuns` 拒绝一侧混有两个批次的记录（`mixed-payload:<边>`），所以没有按场景拼凑批次的做法。
- **何时跑**：
  - 审查轮次结束、PR 头冻结之后跑。两侧都在 PR 头这个框架里，用 `--payload` 换载荷，宿主、CLI 版本、模型和认证方式相同。
  - 评测发现问题，修好后，修复先经审查，再在新的 PR 头上重跑整个「后」批次：载荷变了，旧的「后」批次不再等于 PR 头。「前」批次对下面判定的第 2、5 件仍然成立时复用，否则整个比较集重跑「前」。
  - 两边都不通过的场景按现有规则记回归，挡住这个 PR；如果是 main 自己的缺陷，先单开修复。
- **评测对合并结果有效：一个判定。**记 B 为合并基点（PR 头和 main 的共同祖先），T 为 main 当前的提交，H 为 PR 头。squash 合并的结果，载荷是「T 的载荷加上 H 相对 B 的载荷改动」，框架也一样。下面五件都成立，PR 的前后比较才算比较过合并结果：
  1. B 和 T 的评测载荷摘要相同，B 和 T 之间框架文件逐字节相同：main 自 B 起只可能动了豁免部分，没动框架。PR 已经变基时 B 就是 T，这一件自然成立；
  2. 「前」批次清单的 `payload.evaluatedDigest` 等于 B 的评测载荷摘要；
  3. 「后」批次清单的 `payload.evaluatedDigest` 等于 H 的评测载荷摘要；
  4. 两批清单的 `fingerprint.runner` 等于 H 的运行器指纹；
  5. 在 H 的检出里，两批各自重算 `payloadFingerprint(selectScenarios(<该批清单的 scenarios>, <该批的载荷>))`，等于该批清单的 `fingerprint.payload`。这一件查得出只改了场景定义的框架变动。
  - 框架文件指 `runnerSources`、`scenarioHashSources` 列出的文件，以及 `tests/eval-comparability.test.ts` 枚举的场景模块导入闭包。
  - 第 1、2、3 件一起保证：除豁免部分外，main 合并前的载荷就是「前」的载荷，合并结果的载荷就是「后」的载荷。第 1、4 件保证：合并结果的框架就是评分用的框架。
  - 判定由一个导出的纯函数负责，输入是 B、T、H 三处的评测载荷摘要和框架摘要，以及两批清单；输出 `current`，或静态原因，例如 `base-payload-moved`、`base-harness-moved`、`before-not-base`、`after-not-head`、`runner-differs`、`payload-fingerprint-differs:<边>`。git 读取在 `scripts/eval-batch.ts` 里做。
  - 用到这个判定的有两处，都只调用这个函数：合并前的有效性命令，和下面「复用「前」」的判断。
  - 判定不成立时，先变基（B 变成 T），再按受影响场景命令重跑需要重跑的批次，每侧仍是一个完整的批次。main 自 B 起只动了载荷和框架以外的文件，或只动了豁免部分时，判定成立，不用重跑。
- **复用「前」**：上一个 PR 的「后」批次，满足三个条件时可以直接当本 PR 的「前」：
  - 调用上面的判定，第 2 件和第 5 件对它成立：它的评测载荷摘要等于本 PR 合并基点 B 的；在 H 的检出里重算它整批的载荷指纹不变，也就是它跑过的场景里没有一个定义被本 PR 改过。第 5 件按整批核对，比较集之外的场景改了定义也不复用；
  - 它和本 PR 的「后」批次之间，`batchIncomparability` 没有原因：宿主、CLI 版本、模型、认证方式和运行器指纹都相同；
  - 它含本 PR 比较集里的全部场景。
  - 任何一条不成立，就不复用，整个比较集新跑「前」。合并前，同一个判定再核一次。
- **记录**：每个 PR 的评测记录写进该票的验证记录，内容包括比较集、只跑「后」的场景、各批次目录名、`compare` 结论、契约变更集、合并前有效性判定的输出，以及第 3 步的人工核实。
- 真模型运行仍然只在本机、用专用登录目录（[AGENTS.md](../../AGENTS.md)）。

### 四、发布只和上一个标签比较

- 「前」是上一个发布标签的载荷，「后」是发布候选。两侧在同一个冻结的框架（候选）里跑，范围是全部场景。
- 「前」载荷做不了的场景只建基线。各票的「前后不降」以各 PR 自己的评测记录为准，发布记录里链接这些记录，不再回到各票的历史载荷。
- v0.2.0 第一次用这条规则：v0.1.0 标签里没有契约版本表，所有契约算版本 0，契约项全部只核「后」。
  - 这样做只少了契约项在「前」侧的比较：「后」照样必须全部通过，行为项照常比较。
  - 不为 v0.1.0 补一份版本表：标签已经发布，不能改。
- 发布记录照抄 `compare` 输出里的契约变更集，发布说明列出这一版改了哪些契约、由哪些工单改。

### 五、改契约的 PR

- 工单正文写一节「契约变更」，列出契约 id 和新版本；不改契约的票不写这一节。
- 同一个 PR 里：
  - 改产品和评分器；
  - 在 `eval/contract-versions.json` 给这个契约升版本、记工单号；
  - 新契约要先在 `eval/contracts.ts` 登记。
- 这个 PR 的「后」侧运行，就是新契约版本的第一批记录（重建基线）。不另外跑。
- **核对**：
  - 评测记录里 `compare` 的 `contracts.changed`，要等于工单「契约变更」一节，人工核实第 3 步核这一点；
  - `contractBeforeFailures` 和 `behaviorBeforeFailures` 里的每一项，记录要逐项说明属于哪一种：本 PR 有意改进的行为（工单里写明）；证据显示 main 那次运行里模型自己做错了（写出位置）；没声明的契约变更。
  - 没声明的契约变更，按契约有没有登记分两种：
    - 已经登记的，补上版本号和工单声明，再重新运行 `compare`。只改版本表不改变指纹，批次不用重跑；
    - 没有登记的，要在 `eval/contracts.ts` 登记。这会改变运行器指纹，比较要重跑。分类一致性测试在评测之前就拦下没登记的动作和路径，所以只有测试漏掉时才走到这一步。

### 六、第 3 步人工核实的改动

人工核实的流程从 [26 的发布验证记录](../release-verification.md)「人工核实清单与记录格式」移到 [行为评测](../evaluation.md)，成为每个 PR 和每次发布共用的流程。改动如下：

- **第 1 步**：每个 PR 核实自己的「后」侧和只跑「后」的运行，发布核实「后」和基线批次。和现在一样，只核完成且机器评分通过的运行。
- **第 3 步「场景指纹与可比」**：
  - 现有三条照旧；
  - 加第四条：`compare` 输出的 `contracts.changed` 等于工单声明，这一份的 `excludedContracts` 是它的子集；这一份在 `contractBeforeFailures`、`behaviorBeforeFailures` 里的每一项，记录里都有「五」要求的说明。
  - 删去「`compare` 的子集里不能有「未验证的比较」表里的配对」：这张表不再存在。
- **第 3 步「无「前」（只建基线）」**：只用于新增场景，以及「前」载荷做不了的场景。「无「前」（比较未验证）」这一类取消。
- **记录格式**：「指纹配对」一列追加「契约项只核「后」：<id>（v<前>→v<后>）」，或「无」。
- **第 4 步**：逐项清单不变，仍然只核「后」侧；被排除的契约项由核实者在「后」的证据里照常核对。

### 七、Codex 用量

依据：维护者 2026-11-15 实测，一整轮 252 次运行约占其 Codex 套餐用量的 2%（原话「一次2%」），即每次运行约 0.008%。下表按今天的场景目录估算：117 个场景，用 `scenarioRequirements` 数每个 skill 被多少个场景装入：maa-core 114、maa-daily 52、maa-account 33、maa-setup 18、maa-doctor 15、maa-help 4。只算 Codex 一个宿主；Claude 一侧恢复后同样的数量再来一遍。pass→fail 的每个场景另加 3 次，读保护检查每批约 1.6 万 token，都不大。

| 情况 | 运行次数 | 约占套餐 |
| --- | --- | --- |
| 发布（全部 117 个场景，前后各一次） | 234 | 1.9% |
| PR 改了 maa-core（114 个场景装它，几乎就是整轮） | 228 | 1.8% |
| PR 只改 maa-daily | 104 | 0.8% |
| PR 只改 maa-account | 66 | 0.5% |
| PR 只改 maa-setup | 36 | 0.3% |
| PR 只改 maa-doctor | 30 | 0.24% |
| PR 只改 maa-help | 8 | 0.06% |
| PR 新增 n 个场景（只跑「后」） | n | n × 0.008% |
| 框架 PR、豁免表里的改动 | 0 | 0 |

- 复用上一个 PR 的「后」作「前」，最多省掉「前」那一半。只有相邻的 PR 比较同一批场景、本 PR 没改那一批里任何场景的定义时才省得下；框架改动或 Codex CLI 升级会让复用失效。豁免表里的改动合并到 main，不让复用失效。
- 评测发现问题、修改载荷之后，整个「后」批次要重跑一次（一侧只认一个批次）。下面的举例没有算这部分。
- 举例：一个发布周期有六个改 agent 可见行为的 PR，两个改 maa-core、四个各只改一个 skill（平均约 0.5%）。不复用时约 2 × 1.8% + 4 × 0.5% + 1.9% ≈ 7.5%；「前」全部能复用时约 5%，实际在两者之间。v0.1.0 是一轮约 2%，但留下 33 对比较不了，另有逐个载荷的离线核对。
- 第 3 步人工核实用的是 Claude 一侧的子代理，不占 Codex 用量。

## 验收条件

- [ ] **分类一致性测试**：新测试枚举每一个检查的产出方，包括 `grade()` 的各项、`assessDailyTransaction`、`assessWriterTransaction`、生成文件授权，以及场景目录里落在产品记录路径上的授权、期望改动和期望调用，断言下面几件事：
  - 每个检查恰好有一个标签；
  - 契约检查都指向 `eval/contracts.ts` 里的 id；
  - 注册表里每个 id 都有检查在用；
  - `eval/contract-versions.json` 和注册表的 id 集合相同，每个版本是正整数。
  - 场景目录里每个期望调用的（文件、动作），都登记在某个契约下，或在稳定动作清单里；
  - 新增没有标签的检查、注册表外的产品记录路径，或两处都没登记的期望动作，测试失败。
- [ ] **不连坐，对每个契约各一条**：取 HEAD 载荷上正确做法的证据（宿主替身驱动），只改这个契约的一处细节，断言全部行为项仍然通过，不通过的只有这个契约的项。至少覆盖这几处：
  - 去掉待执行记录的 `versions`；
  - 去掉 `preview` 调用和 `diffFingerprint`；
  - doctor 记录换成 08 之前的 `checks` 形状、去掉 `version` 和 `skills`；
  - 锁文件少一个字段。
- [ ] **反方向**：契约都完好，只改行为，对应的行为项不通过。至少覆盖：
  - 结果未知后重放写入；
  - 被拒后自己设 `closedConfirmed: true` 再写；
  - 改了未授权的配置键；
  - 输出秘密；
  - 调用被禁止的 `doctor.ts repair`；
  - 不调用对应的产品命令，直接手写产品记录。
- [ ] **总判定不变**：现有场景测试和评分自检里，每一份样例的总判定（`pass` / `fail` / `unverified`）不变；只允许 `failed` 里的名字随拆分改变。
- [ ] **契约版本**：`scripts/evaluation.ts` 导出的函数由两侧版本表算出变更集。测试覆盖：
  - 版本相同的契约不进变更集；
  - 一侧缺这个契约，算版本 0；
  - 版本表不是合法 JSON，或版本不是正整数，就拒绝；
  - 评分器的导入闭包里没有 `eval/contract-versions.json`：`tests/eval-comparability.test.ts` 的闭包清单照此更新，只升版本号不改变运行器指纹和场景指纹。
- [ ] **`compareRuns` 的新判定**，每条一个测试：
  - 「前」只在变更集里的契约项不通过、「后」全部通过 → `pass`；
  - 「后」在变更集里的契约项不通过 → `needs-reruns`，重跑三次全过 → `unstable`，有一次不过 → `regression`；
  - 版本相同的契约项「前」通过、「后」不通过 → `needs-reruns`；
  - 行为项两边都不通过 → `regression`；
  - 没有 `items` 的记录 → `incomparable`，原因 `grade-items-missing:<边>`；
  - 两边的项不同 → `grade-items-differ:<场景>`；
  - 现有比较测试的其余断言照旧通过。
- [ ] **`compare` 的输出**：用合成批次目录测试 `contracts`、`excludedContracts`、`contractBeforeFailures`、`behaviorBeforeFailures`、按可比项算的 `passToFail`。「前」载荷的提交读不到版本表时，整体 `incomparable`，原因 `contract-versions-unreadable:before`；提交里没有版本表时算全部为 0，不算读不到。
- [ ] **受影响场景命令**：不调用模型，输出比较、只跑「后」、不跑三类和各自理由。用合成载荷目录测试：
  - 只改 maa-account 的一个文件，比较类正好是装 maa-account 的场景；
  - 改 maa-core 的一个文件，比较类正好是装 maa-core 的场景；
  - 新增或改了定义、装入文件不变的场景，落在只跑「后」；
  - 豁免表里的改动，不产生比较类；不在豁免表里的同一文件改动（例如 `package.json` 改了 `version` 以外的字段），照常产生。
  - 测试里的场景数从目录算出，不写死。
- [ ] **合并时有效性判定**：一个导出的纯函数按「三」的五件事输出 `current` 或静态原因，合并前的有效性命令和复用「前」的判断都只调用它。测试覆盖：
  - 判定的每一项输入各一个用例，只改这一项，结果都不是 `current`；
  - 反方向：PR 没有变基，而 main 在 B 之后改了载荷，或改了框架文件；「前」取自 main 当前的载荷（复用上一个 PR 的「后」，或从当时的 main 新做），而 PR 没有变基。结果都不是 `current`；
  - main 在 B 之后只动了载荷和框架以外的文件，PR 没有变基，仍是 `current`；
  - main 在 B 之后只合并了豁免部分的改动（例如每日 Action 加了一个核实版本、`recordVersion` 加 1），PR 没有变基，仍是 `current`；复用跨过这样一次提交的「后」批次，第 2 件也成立；
  - 被复用的「前」批次里有一个场景的定义被本 PR 改过（不论在不在比较集里），第 5 件不成立；
  - 像 `tests/eval-comparability.test.ts` 列出比较结论的使用方那样，逐一列出这个判定的使用方（有效性命令、复用「前」）；新增一处不经这个函数的判断时，测试失败。
- [ ] **评测载荷摘要**：一个导出函数按豁免表规范化后取摘要，`payload` 命令输出它，批次清单的 `payload` 记 `evaluatedDigest`。测试覆盖：

## 验证方式

先在两个已批准的接缝写失败测试：工具 CLI 和导出函数（`grade`、`compareRuns`、`compareBatches`、契约变更集函数、评测载荷摘要、受影响场景命令、合并时有效性判定和它的命令），以及 skill 外部行为（场景测试经宿主替身驱动）。用真实临时目录，只替代 MAA 进程、adb 和网络；合成批次目录和合成载荷目录建在临时目录里。分类一致性测试和不连坐测试单独运行并留存结果。历史回放只在本机运行，载荷用 `payload --commit` 做在仓库外的临时目录里，跑完删除。真实模型上的第一次应用，是本票之后第一个改载荷的 PR，或者 v0.2.0 的发布比较；在那之前，真实模型上的效果如实记为未验证。

## 实现与交付约定

有代码行为的改动先写外部行为测试，使用真实临时目录，只替代 MAA 进程、adb 和网络。本票不改载荷，不需要模型前后评测；但它改了评分器和运行器，之后的记录和 v0.1.0 的记录不可比，这本来就是框架改动的后果。每个改动包经一个独立审查员审查，原则上最多三轮，记录意见处置和结论。公开前检查改动文件的隐私，经分支、PR 和 squash 合并。

构建与评测使用临时 home，不改动维护者现有 MAA、已安装 skill 或私有生产环境。本票的设计默认值在实现时登记进规格两张来源表。
