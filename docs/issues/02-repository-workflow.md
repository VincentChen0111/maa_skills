## 验收条件

- [x] 建立项目自己的开发约定：测试先行、单个独立审查员、最多三轮、skill 改动前后评测及公开前隐私检查；明确记录每项审查意见的接受/拒绝理由和最终结论的位置。
- [x] 落地本地 Markdown tracker 的六个头字段和五种 triage 标签，维护可检查的工单索引及依赖；GitHub Issues 对外开放，本批镜像 Issue 与本地票互链，不出现两套相互矛盾的状态约定。
- [x] 在 Node 24 上提供离线检查入口；CI 运行脚本测试、已有评分规则自检和隐私检查，未建立的能力如实标明，CI 不调用真模型或真实 MAA。
- [x] 核实 GitHub 密钥扫描和推送拦截已启用，已有配置记录核实结果；本地/CI 隐私检查能拦截合成的私人路径、凭据和账号标记样例，合法公开说明通过；明确每个移植文件的代码、注释和测试数据都需检查，真实账号基线用合成数据替换。
- [x] 准备双宿主原生安装所需的插件/市场描述结构及宿主说明；后续 skill 加入时可沿用，不增加复制安装脚本或重复的共享工具实现。
- [x] 中文 README 开头有英文简介，包含范围、贡献入口、致谢及规格要求的四项免责声明；保留 MIT，提供借用代码许可、版权行、来源提交号的记录方式。
- [x] 维持分支、PR 和 squash 合并流程；不重新放宽已生效的 main 保护。共享工具保持一个可被其他项目引用的实现，外部项目迁移另行处理。

## 验证方式

在干净检出运行离线入口，演示合成隐私正反例及过期索引检查；检查文档链接和描述文件。这里只验证开发闭环，双宿主实际安装验收由 04 完成。

## 依赖理由

01 先统一规则来源，避免把待更正的归属写入开发约定。

## 实现与交付约定

有代码行为的改动先写外部行为测试，使用真实临时目录，只替代 MAA 进程、adb 和网络；skill 改动按同模型、同场景做前后评测，真模型只在本机运行。每个改动包经一个独立审查员审查，最多三轮，记录意见处置和结论；公开前检查所有移植文件及合成样例的隐私，经分支、PR 和 squash 合并。

构建与评测使用临时 home，不改动维护者现有 MAA、已安装 skill 或私有生产环境。沿用本票所列规格决定；新增或修改限制时在规格两张来源表登记来源。
