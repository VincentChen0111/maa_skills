## 要交付的行为

maa-account 生成基建建议报告和可交给 daily 的自定义排班，说明收益依据并完成独立审查。

## 规格依据

用户故事：22、23、24、25、26。涉及章节：共享工具；账号快照与建议报告；五个 skill 和边界。术语使用父规格关联的术语表。

## 验收条件

- [x] 从用户快照中的布局、持有干员和有效技能生成排班建议；移除特定用户的布局和人员硬编码，不把某个用户的安排当通用默认值。
- [x] 至少校验房间容量、计划数上限、同计划不重复干员、键名大小写及 MAA 不能切换生产线；出现未持有干员给出警告。
- [x] 容量、计划数等值来自实际支持的 MAA 版本及核实证据；新增限制或默认值登记到规格两张来源表，不凭经验编造上限。
- [x] 报告说明每项收益的计算依据、条件和未建模部分，已核实与推断分开，列出用户可执行步骤及相关成本。
- [x] 复用 20 的建议报告与独立审查流程；用户明确跳过时标「未审查」，审查通过仍需用户批准才能应用。
- [x] 共享排班生成/检查提供 CLI 和 Markdown 输出，产物放在私有目录；account 不写入 MAA 配置。
- [x] 借鉴外部排班规则时记录来源提交与许可；数据用时获取、样例合成，不携带原个人排班。
- [x] 共享排班检查实现下面「排班方案的 15 项验收门」，每一项对每份方案给出通过、不通过或未核实，并附证据。有不通过的项时，方案不标为可应用，报告写明是哪一项；未核实的项在报告里单独列出，不算通过。15 项是规格「共享工具」里六条校验规则之上的补充，验收第 2 条的现有校验不减少。
- [x] 生成的每个计划都写 `period`（换班时间段）。格式 `hh:mm`、跨天拆成两段，按固定版本的 MAA 排班协议；这个字段由 MAA 图形界面处理，MaaCore 不处理。计划之间时间段重叠时 MAA 选哪一个，核实后采用，结论写进验证记录。
- [x] 排班里的干员名用用户本机 MAA 的干员名表校验，因为 MAA 按名字识别干员；不在表里的名字是校验错误，和「未持有」的警告分开报告。固定版本的资源里有 `resource/battle_data.json`；用哪张表、哪个字段，核实后采用。
- [x] 账号快照、基建技能表和排班检查结果的数据新鲜度用三态表示：新鲜、陈旧、未知。判定条件在实现时定，并写进验证记录。旧的检查结果不能当作当前数据新鲜的证明：快照或技能表变了，检查重新跑。
- [x] 写排班文件时：只写私有目录内的路径，路径规范化后落在私有目录之外就拒绝；用原子替换写入；在已有排班文件上修改时，保留文件里本工具不认识的字段。

排班方案的 15 项验收门。其中的数值是游戏机制，不是本项目定的上限；心情上限 24、宿舍床位总数 20、菲亚梅塔目标每小时消耗不超过 2，都在固定游戏数据或注明出处的资料上核实后采用，核实不了的检查项输出「未核实」。

1. 每名干员在每个班次里最多出现一次，宿舍也算；同一个周期里不在同一干员的异格形态之间切换。
2. 每个名字都在账号快照的持有清单里，不在的按验收第 2 条给出警告；房间存在；人数不超过房间容量。
3. 计划数等于班次数；房间数和用户的布局一致。
4. 每名干员单次连续上班的时长乘以净心情消耗，不超过心情上限；整个周期的心情消耗不超过恢复速度乘以休息时长。
5. 没有干员每个班次都在岗。菲亚梅塔的目标干员除外，这时该目标的心情消耗不超过每小时 2。
6. 宿舍可用床位按床位总数减去常驻宿舍的人数计算，休息的人数不超过它。
7. 跨设施的组合成员，和它们依赖的挂件干员，排在同一个班次。
8. 贸易站和制造站里互斥的技能或组合不同时安排。
9. 干员的技能和所在房间的产物匹配。
10. 控制中枢里没有重复的同类光环，并且满员。
11. 每个时间节点只有一个无人机目标；菲亚梅塔换班只发生在班次开始时，每个节点最多一次。
12. 报告的效率等于基础、技能、全局加成三部分之和；每日数值按班次时长加权。
13. 交付的排班文件，和对同一结果重新做一次确定性导出得到的文件相同。
14. 用户比计划晚上线或早上线时，方案仍然成立。
15. 措辞审计：没有证明是最优的方案，不称最优。

参考，只对照思路，不复制代码：枚举、整数规划、模拟、审计的管线可参考 [KayChung17/arknights-base-skill](https://github.com/KayChung17/arknights-base-skill)（代码 MIT）；它打包的数据不进本仓库，规格已限定它的技能数据只用来交叉核对。自定义基建 JSON 的校验可参考 [dongwlin/La-pluma-next](https://github.com/dongwlin/La-pluma-next)（MIT）。检查清单的思路另见 [GuanxiYi1987/ark-base-schedule](https://github.com/GuanxiYi1987/ark-base-schedule) 和 [Closure-RIIC/RIIC-knowledge](https://github.com/Closure-RIIC/RIIC-knowledge)；这两个仓库的许可以各自的声明为准，实现时核对，核对之前只取思路。排班协议见固定标签 v6.21.4 的 [MAA 基建排班协议](https://github.com/MaaAssistantArknights/MaaAssistantArknights/blob/v6.21.4/docs/zh-cn/protocol/base-scheduling-schema.md)。

## 验证方式

用不同合成布局和名册验证有效排班、超容量、计划超限、同计划重复、大小写错误、生产线不支持及未持有警告；验证报告审查和预算结果。2026-11-13 补充：15 项验收门每一项至少有一份通过和一份不通过的合成样例；另验证 `period` 的格式和跨天写法、名字不在 MAA 名表里的错误、快照变化后旧检查结果被标为陈旧，以及越出私有目录的路径被拒绝。

## 实现与交付约定

有代码行为的改动先写外部行为测试，使用真实临时目录，只替代 MAA 进程、adb 和网络；skill 改动按同模型、同场景做前后评测，真模型只在本机运行。每个改动包经一个独立审查员审查，最多三轮，记录意见处置和结论；公开前检查所有移植文件及合成样例的隐私，经分支、PR 和 squash 合并。

构建与评测使用临时 home，不改动维护者现有 MAA、已安装 skill 或私有生产环境。沿用本票所列规格决定；新增或修改限制时在规格两张来源表登记来源。
