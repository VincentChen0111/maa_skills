## 要交付的行为

maa-daily 查找和核对指定关卡的作业时，对没写要求的旧作业、需要借助战的作业、评分不足的作业和接口的模糊匹配给出更准确的结论，并把依据写进报告；每项改动都有固定来源的核实记录。

## 验收条件

- [ ] 先核实，再改：下面每一项先在固定来源上核实对应的事实，把来源、固定提交和结论写进[作业接口核对](../stage-jobs-sources.md)。核实不成立的项不实施，在验证记录里写明理由。作业站一侧先核实线上服务实际运行的后端仓库和提交；现有记录固定的是 MaaCopilotServer `e3f9cbf`，它是否仍是线上版本没有核对。
- [ ] 没写要求的旧作业（核实后采用）：干员条目没有 `requirements` 时，不再只凭持有就判满足。核实 MAA 在固定版本上对这类条目的实际处理，再决定给什么默认要求，例如按稀有度给出默认的精英阶段和等级。默认要求和作业原文分开显示，标明是推定值。默认值的具体数字在采用时登记到规格两张来源表；没有定出有依据的数字之前，这类条目记为「要求未写明，待核」。
- [ ] 借助战（核实后采用）：允许一份作业有一个位置由助战干员补上。先核实固定版本的 MAA 自动编队是否支持助战补位，以及对应的设置。支持时，缺一人的候选标为「需借助战」，写明缺的位置和要求，和完全就绪的候选分开排列，批准时由用户点名；不支持时不实施。借助战不放宽其他位置的核对。
- [ ] 评分（核实后采用）：读取接口返回的点赞、点踩或评分字段，连同票数写进候选的证据。先核实这些字段的含义，以及「票数不超过 50 时带评分不足标记」这一说法。候选排序可以把评分不足或好评率低的排到后面并标出原因。是否设门槛、门槛是否随票数变化，在采用时决定；有同类项目用过「票数越多、要求的好评率越高」的做法，数值只作起点参考。任何门槛的数字都登记到规格两张来源表。评分只影响排序和提示，不代替要求核对，也不代替用户批准。
- [ ] 关卡后缀（核实后采用）：核实固定关卡表里，除突袭的 `#f#` 之外是否还有带后缀的关卡 ID 写法。有的话，检索和筛选要覆盖到，并补测试；没有的话只把核实结论记下来。
- [ ] 动作里的干员名（核实后采用）：扫描作业动作里引用的名字，找出没有出现在 `opers` 和 `groups` 里的干员，这样的作业记为待核并列出名字。扫描时排除干员组的组名和装置名。先在固定版本的作业协议上核实动作的 `name` 可以引用哪几类对象。
- [ ] 接口语义（核实后采用），逐条在后端源码上核实，再决定查询和筛选怎么改：`level_keyword` 是对关卡名、关卡 ID、章节 ID 的模糊匹配，没有匹配时会退回到按文档关键字搜索，可能返回大量无关结果；`operator` 参数里前缀 `~` 表示排除；票数不超过 50 时带评分不足标记。核实成立时，报告要能分清「这一关没有作业」和「查询退回到了关键字搜索，结果与这一关无关」，三页读完而没有一条属于这一关时写明覆盖不足，不写成没有作业。
- [ ] 已交付的行为不回退：15 的现有测试保持通过；报告指纹、批准绑定和派生执行内容的校验不变。匹配结果的结构有变化时报告哈希随之变化，旧报告上的批准不沿用。
- [ ] skill 正文和 `skills/maa-daily/references/stage-jobs.md` 随实际交付的改动更新；六个 stage 场景按同一模型做前后评测，新增的行为各加场景。

参考，只对照思路，不复制代码：匹配规则可参考 [OriginiumLab/MAA-PRTS](https://github.com/OriginiumLab/MAA-PRTS)（MIT）。作业站后端和 MAA 是 AGPL-3.0，没有许可证的来源同样处理：只取事实和思路。

## 验证方式

每项改动先在 `stage-jobs.ts` 的命令行和导出函数接缝写失败测试，用合成作业和合成账号快照：没写要求的条目、缺一人、不同票数和好评率、带后缀的关卡 ID、动作里引用了未声明的干员、查询退回关键字搜索。网络只用边界替身，不依赖线上接口的实时内容。核实记录和测试一起提交；没有核实的项如实记为未实施。

构建与评测使用临时 home，不改动维护者现有 MAA、已安装 skill 或私有生产环境。沿用本票所列规格决定；新增或修改限制时在规格两张来源表登记来源。
